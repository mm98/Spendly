16a Actions inventory
Every control drawn in the mockups, what it does, and what the user sees afterwards. Compiled by walking each file rather than from memory, so this is what is actually on the pages — including ten controls that had no described behaviour anywhere. Those are resolved at the end, in 16b.
HOW TO READ THIS
"After" is the observable result, because that is what the user judges. toast + Undo means the change applies immediately and is reversible for the toast's life. dialog means it cannot be undone and is confirmed first. Nothing in this document contradicts that pairing — if an action is reversible it does not get a dialog, and if it is not, it does not get a toast.
Global actions live in the shell; page actions do not. Scan receipt and New order sit in the top bar because they belong to the app, not to whatever page is open. That is not an exception to the locked-shell rule — the rule is that a page may not put its own actions up there.

16b Loose ends found, and closed
Ten controls were drawn with no behaviour described anywhere. Each is resolved below. Three need a product answer rather than a design one and are marked as such.
RESOLVED HERE
Export CSV / Export. Appeared on four screens meaning four things. Now one behaviour: it exports the current filter or drill state, never the page and never the whole account, and the button label carries the count ("Export 128 orders"). One row per item line, with order fields repeated, because that is the shape the import reads back — export and import are the same column set, which is what makes a round trip possible.
Save current (saved views). Stores query, facets and sort under a name, listed above the facet rail. It stores the filter, not the result — opening a view re-runs it. Renameable and deletable from the list; a view is never shared, since there is one user.
Archive (vendor). The middle option between keeping and deleting, and the answer to 5c's "no orders in 12 months". Hides the vendor from pickers and facet lists while its orders, totals and history stay exactly as they are. Reversible, so toast + Undo, and archived vendors are reachable behind a filter in the library.
Duplicate last order (Home). Applies 8a's duplicate to the most recent order without opening it first. Identical rules — no date, no status, no attachments — and it opens unsaved, so the shortcut can't create anything by accident. Hidden when there are no orders.
Reuse mapping. Applies a previous import's column mapping to the newly picked file by matching column names. It always lands on the mapping step with rows pre-filled, never straight on preview: a file with the same headers can still hold different data, and the confirmation step is the point of the flow. Columns that don't match are left unmapped and flagged.
Change password. A dialog — current, new, confirm — not inline fields, so it is never half-filled inside a card that saves other things. Success is a toast; other sessions stay signed in, since signing yourself out of your phone for changing a password on your laptop is a punishment for good hygiene.
Open full size (scan review). Opens the same viewer as 12b, with the receipt as its only file, so the small print can be read without leaving review. Edits in the panel behind it are untouched.
NEEDS A PRODUCT ANSWER
See theirs (6d, the two-tab conflict). Recommendation: it opens the other version read-only beside yours, and the only actions are keep-mine and take-theirs. There is no field-level merge — for one user in two tabs that is more machinery than the problem deserves.
Duplicate name (6c). A vendor or category name colliding with an existing one. Recommendation: warn, don't block — offer "use the existing one" as the primary and let the duplicate through as secondary, since two vendors can genuinely share a name.
Export format. CSV is drawn. Recommendation: CSV only, UTF-8 with BOM so Excel opens Danish characters correctly, and the user's own number format. XLSX only if someone asks.
DRAWN IN 16c
Six of the ten needed layout, not just a sentence. They are below: saved views, the archived state, the password dialog, export, the conflict view and the duplicate-name warning. The other four reuse screens that already exist.
TWO PATTERNS THE AUDIT CONFIRMED
Every destructive action has exactly one dialog, and every reversible one has exactly one toast. Nothing in the set has both, and nothing has neither. Delete order, bulk delete, merge and discard-scan are dialogs; line delete, status change, category add, archive and import are toasts.
Every "See X" link is a filter handoff, not a new view. See in Statistics, Open in orders, the Needs-a-look rows and the monthly summary rows all carry state into a screen that already exists. No screen in the set is reachable only through one link.

NOTES FOR IMPLEMENTATION
No visible per-row buttons, deliberately. A pencil on every row is a third way to reach somewhere the row click and the menu both already go, and it costs 48px of a column budget 15a keeps tight. The row's own hover fill and pointer are the affordance; the ⋮ is the overflow.
The item line in 1b is the exception, for a different reason. That row expands in place instead of navigating, so there is no address to fall back on and no menu — the pencil is the only signal it is editable. A row that navigates never needs one.
Every data row in the app ends in the same 40px actions cell, holding the ⋮ and nothing else. What the menu contains is a rule, not a judgement per screen.

WHAT IS VISIBLE, WHAT IS IN THE MENU
Visible: the one action that is the row's purpose. Edit on an order, Open on a vendor. One button, two at most — a third is a menu that has escaped.
In the menu: everything else, in a fixed order — the constructive ones first, then a divider, then the destructive one last and alone.
Destructive is never a visible row button. Delete is one pixel from Edit at 30px apart; behind a menu it needs two deliberate movements, and it still opens a confirm dialog after that.
The menu never holds something unavailable elsewhere. Every entry is reachable from the record's own page too. A menu is a shortcut, not the only route.
It does not scroll and does not nest twice. One level of submenu, for Set status only, because that is a value list rather than a set of actions.
BEHAVIOUR
The cell is 40px and always occupies space, whether or not the row is hovered. The ⋮ fades in; the column does not appear, or every row shifts on hover.
On touch the buttons are permanently visible at 44px, as with the pencil on item rows.
Opening the menu holds the row in its hover state and inverts the ⋯ button, so it is clear which row the menu belongs to once the pointer has left.
The panel is 226px, radius 10px, shadow 0 6px 16px rgba(27,26,23,0.08), anchored to the button's right edge and flipping above when there is no room below.
Clicks inside the cluster do not open the row. Every button stops propagation — the single most common bug in this pattern.
Keyboard: the ⋯ is in tab order, Enter or Space opens, arrows move, Esc closes and returns focus to the button. It carries aria-haspopup="menu" and an aria-label naming the row — "More actions for Indbo Møbler", not "More".
Right-clicking the row opens the same menu at the pointer. Same component, same entries.
While a selection exists the cluster is hidden — bulk actions own the rows then, and a per-row menu next to a checked box is ambiguous about what it applies to.

RULES
If it does not respond to a click, it does not hover. Cards, KPI figures, section headers, status pills, the totals card — all inert. This is the rule that keeps hover meaningful.
One fill per depth. A hovered button inside a hovered row uses the lighter #f7f6f2, so the two are distinguishable. Never stack the same fill twice.
Hover never moves anything. No lift, no scale, no shadow appearing, no border thickening — a border going from 1px to 2px reflows the row. Colour and opacity only.
Selected beats hover. A selected row stays #e7efe8 and does not shift on hover; a checked chip does not change. Losing the selection colour to a hover is the same as not showing it.
120ms ease on the colour, in both directions. Nothing longer — a slow hover on a list feels like lag.
Focus is not hover. Keyboard focus is always the green ring from 14a, never the hover fill, so the two are never confused. A row can carry both at once.
Guard with @media (hover: hover). Without it a touch device keeps the hover fill on the last row tapped, which reads as a wrong selection.
ON DARK
Hover lightens rather than darkens, matching the elevation rule in 12a: row hover is #2a2621, icon-button hover #38332c, selected #1f3328. Same meanings, same 120ms.
Every value is a token, so no component contains a hover colour literal — --surface-hover flips with the theme and the component never knows.
16f What clicking a row does
Every list in the app has clickable rows, and they do three different things. The difference is not arbitrary — one rule produces all three.
THE RULE
A click takes you to wherever that row's detail already lives — and it never opens an edit form.
If the detail is a route, the click navigates. If it is a panel on the same page, the click selects. If it is the row itself, the click expands. Nothing has to be remembered per screen, because the layout already says which of the three it is.
The second half matters as much as the first: a row click always lands you somewhere you can read. Editing is a second, deliberate action — the pencil, the menu, or the Edit button. A list where clicking opens a form is a list you cannot browse without risking a change, and the whole point of a row is to be looked at.

NOTES FOR IMPLEMENTATION
A clickable row carries cursor: pointer. On the row itself, not only on the link inside it. The hover fill is a promise that the row is clickable, and a fill without a pointer half-makes it — the hover state then reads as decoration and people go hunting for the real target. This applies to all three kinds, including the facet row and the item line.
The row is the touch target, not the control inside it. A facet checkbox is 19px and an item-line pencil is 28px because they are glyphs; the row around them takes the full 44px on touch, with the glyph centred. Sizing the glyph up instead makes the row look like a form and still leaves most of its width dead.
Selection is #e7efe8, hover is #f0efe9, and neither is #f7f6f2. The quiet grey means inert. A selected row tinted with it is indistinguishable from a disabled one, and from its own hover state — which is what makes a list-and-panel layout feel like nothing happened when you click.
What must not trigger the row action. The checkbox, the ⋮, every icon button in the actions cluster, the drag handle, and any link or chip inside the row — all stop propagation. Getting this wrong means every attempt to tick a checkbox navigates away, which is the most common bug in a clickable table. It matters most where a row is both selectable and navigable: the order row's checkbox selects, and everything else in it navigates.
Where the click navigates, the row is an anchor. An <a> wrapping the row content, or a real href on it — not an onClick with a router push. That is what makes ⌘-click, middle-click, "open in new tab" and the status bar preview work, and all three are free if the element is an anchor and impossible if it is not.
Where it selects, the row is a button. No href, because there is no address for "vendor 4 is showing in the panel" — and offering ⌘-click on something that cannot open in a tab is worse than not offering it.
Keyboard is the same everywhere. Rows are in the tab order, Enter does what a click does, Space toggles the checkbox where the row has one, and the focus ring is the standard 3px rgba(29,77,51,0.12) on the row rather than on something inside it.
Hover is the contract. Any row with the #f0efe9 hover fill and a pointer cursor is promising it does something. A row that does nothing gets neither — an inert row that lights up on hover is a broken promise, and it is how a user concludes the app is unreliable.
Double-click is never a separate action. On a navigating row the second click lands on the next page; on a selecting row it is harmless. Nothing anywhere requires a double-click.
