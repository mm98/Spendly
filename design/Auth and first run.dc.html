20a Sign in, and create an account
Email and password, open registration. One card centred on the canvas, 400px wide, no marketing beside it - this is a tool someone already decided to use. These are the only screens in the app that render outside the shell, so the card owns its own centring.
NOTES FOR IMPLEMENTATION
Intent. Sign in and register are one component with a different field set and primary label. Two fields against three; nothing else differs, so they share one layout, one error slot and one submit path.
Sign-in errors are deliberately vague, register's are specific. A failed sign-in must not reveal which half was wrong - that confirms whether an email has an account. Register has nothing to protect yet, so it names the field and offers the useful next step.
Stay signed in is checked by default and worded as a duration rather than a promise. On a personal receipt tracker the realistic alternative is a weaker password written down somewhere.
Desktop vs mobile. Below 480px the card goes full width at the phone's own 16px inset, with 48px fields. The primary button is already full width, so nothing else changes.
Easy to get wrong. Enter submits from any field. Email is type="email" and autofocused, with autocomplete="username webauthn" on sign in, so the browser can offer a saved passkey from the field, and email on register; password carries autocomplete="current-password" on sign in and new-password on register, or the browser offers the wrong thing. Email format is checked on blur and on submit, never on keystroke - a half-typed address is not an error.
Passkeys sit beside the password, never instead of it. Two ways in: the browser offers a saved passkey from the email field as the page loads (WebAuthn conditional mediation), and Sign in with a passkey opens the device's own prompt for browsers that do not offer it in the field. iPhone, Android and 1Password answer the same request; the passkey is discoverable, so no email is needed first.
A cancelled prompt says nothing - the form is still there. A passkey the account does not know shows the vague sign-in error above, worded "That passkey didn't work. Try again, or use your password." Lockout pauses passwords only; a passkey still signs in.

20b Confirming the email address
Registration creates the account but leaves it unconfirmed. A link goes to the address, carrying a single-use token; following it confirms and signs in. Until then the account exists and can sign in, and an order can be typed by hand, but scanning and importing are held - a receipt filed against an address nobody can reach is a record with no owner.
NOTES FOR IMPLEMENTATION
One token component, two uses. Email confirmation and password reset are the same mechanism - a single-use token with an expiry, arriving as a link, landing on a page that has to handle valid, already-used, expired and malformed. Build it once; the only difference is what happens on success.
Expired is not an error, it is a resend. The most common path to this screen is a link opened a day later. The primary action is always "send a new one", never a message telling the user what went wrong and stopping.
The banner is amber and dismissible for the session, not a modal. Typing an order by hand, Settings and signing out all still work, so blocking the whole app behind confirmation would hold back far more than it protects.
The address cannot be changed in the app. Settings shows it read-only, and none of these screens offers a way to change it.
Easy to get wrong. Tokens are consumed on use, so a link opened twice - mail clients prefetch - must show "already confirmed" and not an error. Resend is throttled with a visible countdown rather than a disabled button.

20f The emails
Four transactional messages - the confirmation link from 20b, the reset link from 20c, and a notice whenever the password changes or a passkey is added - each the auth card carried into the inbox: the mark, a heading, one line, one button. Then the status email, weekly or monthly, chosen under the email address in Settings (11a): the period's figures and lists in one card.
NOTES FOR IMPLEMENTATION
Send-ready files. emails/confirm-email, reset-password, password-changed and passkey-added, each an .html with a .txt beside it, sent together as multipart/alternative. Sender, subjects and merge fields are in emails/README.md. The specimens below render those files with sample values merged in.
Built for mail clients, not the browser. Tables and inline styles, no web fonts (Poppins where installed, then Helvetica), a VML button for Outlook, and a dark block that maps to the dark tokens. The card keeps the auth panel's values: 400 wide, 16 padding, the 64 mark, the small button.
Every link is also written out as text under the button, for clients that strip or block it.
Password changed is sent on every change - from Settings and from the reset flow alike - to the account's address. Its button opens /reset with the address filled in rather than a token, so it never expires. It carries no link that undoes the change.
Passkey added is sent each time one is added, naming it as the device reported it. Its button opens Settings, Account, where the passkey can be removed. Removing one sends nothing, and resetting the password leaves passkeys as they are.
The status email is one template, emails/status, for both Weekly and Monthly, and emails/status-quiet for a period with no orders. Weekly is sent Monday at 08:00 for Monday to Sunday just ended; Monthly on the 1st at 08:00 for the month just ended, both in the account's time zone. Nothing is sent while the setting is None, which is the default for every account. The sections are Mustache blocks; fields and rules are in emails/README.md, and the specimens merge emails/status-sample.json.
Order in the card: the period, three tiles (Spent with the comparison, Saved, Orders), limits exceeded, Budget (monthly only), top 5 categories, the latest 5 orders, bookmarks added in the period, Needs a look, then Open Spendly. A section with nothing in it is left out, rule and all; the limits box is absent when no limit was passed.
Budget shows costs only. Last month's real costs against the expected costs, and the costs expected in the new month. Income and Left over never appear in the email, whatever Show income was last set to in Budget (21a).
A weekly email states limits for the calendar month so far, since limits are monthly: "11.260,00 kr. of 10.000,00 kr. in October so far". A saving is an amount, green, under the order amount; a zero saving is grey.
Dates follow the account's language, as everywhere in the app: in a Danish account the email reads "in Oktober so far" and "12. - 18. okt. 2026" while the sentences around them stay English. Only month and weekday names change; the numbers already follow the account's number format.
Stop these emails opens 8 to 10, the answer card from 20b: Status emails stopped, Already stopped, or That link has expired after 60 days. A newer email's link works while an older one has expired.
The tiles stack below 480px, and the card keeps one column at every width. Stop these emails sets the setting to None without signing in, from a single-use link.
Easy to get wrong. Reset sends nothing to an address with no account, while the page says the same either way (20c). Every merged value is HTML-escaped; a name is user input.

20e Where these sit in the chrome
None of these are popups. They are routes, at three levels of chrome - and which level a screen belongs to follows from one question: is there a signed-in user, and is there anything worth navigating to?
NOTES FOR IMPLEMENTATION
Routes, not modals. A reset link has to be openable from an email, so /reset?token=… must be an addressable page. A modal also implies something behind it that the user could return to, and at sign-in there is nothing behind it. Back and forward work throughout.
Two layout shells, not one with pieces hidden. An AuthLayout (centred card on the canvas) and the AppShell from 9a. Rendering the app shell with its sidebar suppressed leaves the sidebar's data hooks mounted and fetching for a user who may not exist yet.
First run uses AuthLayout even though the user is signed in. A sidebar reading "0 orders · 0 vendors" beside a question about currency is navigation to nowhere, and the currency answer changes how the shell renders every amount. The shell appears once there is something in it.
Easy to get wrong. An unauthenticated hit on any app route redirects to sign-in carrying the intended path, and lands there after signing in - a receipt link shared to yourself should open that receipt, not Home. A signed-in user hitting sign-in redirects to Home. A signed-in user who has not finished first run is redirected into it from every app route.

20d First run
Two questions, both of which change how the whole app reads and neither of which has a safe default: the currency every amount is written in, and one category to file the first order against. Then Home, with its empty states doing the rest.
NOTES FOR IMPLEMENTATION
Two steps, and a hard stop there. Both are prefilled from the browser locale, so submitting without changing anything is a valid path. Every further preference lives in Settings - an onboarding that asks six questions gets clicked through, and then none of the answers mean anything.
Skippable, and it says so. Skip creates the suggested category and keeps the locale currency. Someone who wants to see the product before configuring it should be able to.
Category, not categories. One is enough to file an order; more can be created inline from any order form. A grid of twelve suggestions invites picking all of them, and then the facet list is full of empty categories on day one.
The monthly limit is not asked here. A limit set before any spending exists is a guess, and the pace marker against a guessed limit teaches the wrong thing. Home's empty state offers it once there is a month of data.
Desktop vs mobile. Same card, full width below 480px, and the currency step uses a full-screen combobox sheet per 15b.
