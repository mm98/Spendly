C Component library
The twenty controls named in Input types 14a, plus the list, menu, card and gauge the pages are built from - written once as generic, reusable components. Values live in styles/tokens.css, components in styles/components.css, and no element on this page carries a style attribute.
How to use this
A card's action fills the width of its footer. One solid button spans it, a pair splits it with --split into equal halves, and three is not a footer - it is a menu. A --text button is the exception: it is a link, and a link stretched across a card reads as a button while behaving like navigation, so it keeps its own width at the left. The card is a column, so an action that hugs its own text reads as floating in the space beside it, and two cards side by side end up with buttons of two different widths for the same action. The component does this from the structure, so no page states it: .sp-card__footer > .sp-btn:only-child is full width. Where the content directly above is a bordered well, the footer drops its own rule - two separators with nothing between them is one too many.
Two files hold every decision. tokens.css is colour, spacing, radius, type and control size. components.css is the components built from those tokens. A page imports both and writes markup only.
Class names are roles, not pages. .sp-field, .sp-mark, .sp-chip - never .orders-row. The same class serves orders, vendors and categories.
Native element per job. A field is <label> plus <input>, a list is a <table>, a menu is a <menu> of <li><button>, a measurement is a <meter>. Hover, focus, checked, disabled and validity are the element's own states; nothing here simulates one.
Data belongs to the page. Labels, counts and figures below are example data. Only what the notes name is fixed.
Touch is the same component. A touch surface adds .sp-touch: control height goes to --control-h-touch and buttons fill the width. Nothing is redrawn.

    Uses
    c2 for the mark on every row, c5 for the select boxes, c6 for chips, the status pill, the compact bar actions, c9 for the record menu behind ⋮, c16 for what a card's clip opens. Each is that component unchanged - same markup, same dimensions, same states; this one adds no variant of it.
    Slots
    The list owns its toolbar - the record count and their total - and nothing else. A page action that happens to sit there, an export or a report, is passed in by the page as a trailing slot and is the compact button (c6); the list neither defines it nor knows what it does. Selection is optional. A list carries boxes only where the page offers actions on several records at once; otherwise it has no box column and no bulk bar, and the user acts on one row at a time through its menu. Both are the same list: adding selection adds a first column and one bar, and changes nothing else. The list has two renderings of the same records, and the page chooses between them: rows, and cards. Both carry the same chrome - the bar stating how many records and their total, the bulk bar that replaces it once something is selected, and the footer stating how many of how many are shown with Load more. Only the placement differs: in rows the bars sit inside the list border, above the cards they stand alone and carry their own border and white ground. A row carries: select box, mark, title, subtitle, any number of data cells, status, amount with an optional secondary line, record menu. The page decides which cells exist and in what order - every one of them except the title is optional, and a list that drops one drops the column with it rather than leaving it empty. A list about records the user is already looking at, as the slice list in Order statistics 5c, carries no mark: the title and its reference identify the row, so a photo would only repeat what the page above it already showed. Every rendering except the row drops the reference too, having no column to put it in. A card carries the same things in a different shape: the record's photos across the top, with its select box and the record menu laid over them; then title and subtitle with the status beside them, its chips, and a footer holding the date, the item count, what was saved and the amount. The box and the menu each sit in a hit target of their own rather than being tapped directly, so the graphic keeps its size while the target grows to --control-h-touch on touch. The menu sits over the photo strip rather than in the footer, so the amount stays hard against the card's right edge and the actions sit with the select box, above the record rather than inside it. It carries what a row's menu carries, plus the attachments the strip is showing (c16). A row has no photo strip, having no photos to put one on, so its menu is the last cell instead. Nothing is in a card that is not in a row.
    The number of pages loaded is part of the address (?pages=3), so Back, a reload, a bookmark, the menu link and Save or Cancel on an edit page bring back the same rows. It resets on any filter, search or sort change, and a saved view does not store it.
    Fixed
    A real <table> with <thead>, <th scope="col"> and <tbody>. Cell padding --sp-12, outer --sp-16, rules --line-2 between rows, --line under the header. Cards sit on .sp-cards--fluid: as many as fit at --card-min-w (280px) or wider, one column below 572px, with no breakpoints of their own (Order list 2c). The bars and footer sit at the column's own gap above and below it. A card is --r-card on --surface inside a --line border, its photo strip 116px with 1px between panes, the box, the clip and the count over it inset --sp-16 so the box lines up with the select all in the bar above, the body on the same --sp-16 margin with its lines --sp-10 apart, and a footer above a --line-2 rule that sits --sp-4 below the chips and --sp-10 above the date, its two stacks top-aligned so the saved line hangs beneath the date rather than pushing it off the amount's baseline, and the amount --t-20 at 700. Every footer is the same height on every card, because the saved line is always there: nothing saved states it as 0,00 kr. in --ink-4 rather than dropping the line, so a grid of cards does not step up and down with what each record happens to hold. Rows are a table, so a header cell and the column beneath it cannot drift apart: the box, date 104, count 90, status 120, amount 152 and menu --menu-col are fixed, the flexible column takes 21%, and the title states no width at all. That last one matters: a fixed table spreads whatever the stated columns leave over every column that has a width, so stating them all makes the box and menu columns grow past their controls on a wide screen. One unstated column absorbs the slack instead, and it has to be the title - the column with text to give, which truncates - so every other column stays the size it says. The box column is --sp-16 of inset plus --box, and the menu column --menu-col without side padding, so each is exactly its control. The box, the mark and the title read as one run at --sp-12. Marks are --mark-medium, and a chip truncates rather than wraps so row height never changes with width.
    States
    Which rendering shows is not a CSS state: a table row and a card are different markup, so the list renders one or the other. Rows and cards are the user's choice above 640. Below it there is no choice: a row has no room for columns and renders as .sp-card sp-card--row, which is that row with its fields dropped rather than a third rendering: the title with its amount, then one line of data. The chips and the status pill go with them - at that width they cost a line each and identify nothing the title does not, and the four-up card grid is not offered at all - a phone screen holds one card, which is the row again. The specimens stand that breakpoint in with .sp-touch inside a phone frame, so both can be seen at once on one page. Nothing selected - the bar states how many records and their total. Some selected - the same bar, in --green-tint, states how many of how many; the head box is indeterminate and the selected rows take --green-tint. Every row selected - the head box is checked and the head takes the tint too, so the whole table reads as selected; the count drops the "of". The bar never appears in addition to the summary: it replaces it, in the same place and at the same height, the moment the first row is ticked, and reverts to the summary when the last one is cleared. Nothing shifts. Hover --hover · selected aria-selected="true", hovering then --green-tint-2 · empty cells show a dashed chip, a dashed mark or a hyphen · data-void="true" strikes title and amount, drops to 0.6 opacity and leaves the record out of every sum.
    Actions
    Select all - in rows this is the box in the header row; in cards there is no header row, so it sits in the bulk bar at the left of the count of selected records, which is only on screen once a card is selected. The cards bar itself carries the count and the total, never a box. Either way it takes every record loaded, not every record matching the filters - that is the separate Select all N matching step (Order list 2h). Clicking it when empty or dashed selects what is loaded; clicking it when ticked clears it. Row box - adds or removes one row, and shift-clicking a second box takes the run between them. The bar's actions - each opens a popover from the bar itself, so the selection stays visible behind it, and nothing is applied until Apply. Set status replaces a single value, so it is a radio list, and each option carries how many of the selection already hold it; it may offer one switch that follows from the choice, such as setting the delivery date with a Delivered status. Add category is additive and multi-select, so existing categories stay, and a category only some of the selection carries shows as mixed rather than on. Each panel states in words what it will do to how many records - "Replaces the status on both orders", "Added to both orders. Existing categories stay." Export takes the selection only, not the filtered list. Delete confirms first, in the dialog that names what will happen (c13). Escape - clears the selection. Selection survives Load more but is dropped when the filters, the search or the sort change, since the records it referred to are no longer in front of the user. Click a row - opens the record. Click a box - selects, and the toolbar becomes the bulk bar. Shift-click - selects the range. Header box - selects everything loaded. Click a chip - filters by that value. ⋮ or right-click - opens the menu shown on the first row; Escape closes it and returns focus to the ⋮. Keyboard - up and down move, space selects, Enter opens. Screen readers read a row as its title, then its status and amount; the checkbox is labelled by the row it selects, and the header checkbox states how many are selected. The sort, the page and the selection all survive going into a record and back - only leaving the list clears the selection.
    Touch - the row becomes .sp-card sp-card--row: tap opens, long-press selects, swipe left reveals the two actions the page marks primary. No ⋮, no hover. A card drops fields rather than shrinking them, so what is left is the mark, the title, the amount and one line of data; the reference, the chips and the status go with the columns, and everything beyond that lives one level deeper, in the record. There is no menu on the strip either - a touch card has no photo strip, and long press does what the menu did.
    Click a card - opens the record: an order card opens the order; a bookmark card (22a) opens /bookmarks/:id/edit from anywhere below its picture strip, while the strip itself is a link to the bookmark's URL in a new tab. A category chip and the card's menu keep their own action and stop the click there. The whole card carries the pointer and the hover border because every part of it acts.
    Bookmark card head - sp-record__head--chips puts the categories right of the name, at most a third of the width: the first as a chip that sets the category filter, the rest as one static "+N" chip. On touch the acting chip keeps the chip's height and takes the touch height as an invisible hit area, so the head is the same height with or without categories (7a, Bookmarks).

    Selecting rows
    Dash selects; it never clears. A partial selection is work already done, and losing it by clicking the box that represents it is the outcome nobody predicts. Clearing is what the Check state does, and the bulk bar carries an explicit Clear as well.
    The checkbox is the only selecting target. Clicking the row navigates instead - 16f. The checkbox and its 44px hit padding stop propagation.
    Shift-click selects a range from the last row clicked to this one, in the order currently displayed. Re-sorting does not re-anchor it; the next plain click sets a new anchor.
    The count in the bulk bar is authoritative, not the ticks. Every action reads that number. If the two disagree, the number is right and the render is wrong.
    Two shapes of selection, one piece of state. Either a set of ids, or a flag meaning "everything matching the current filter" held alongside that filter. The second is not a list of 128 ids: an action on it sends the filter to the server, not the ids, so it stays correct if a row was added since the click.
    Filter, search, sort and page-size changes clear the selection - including the filter-wide one - with no warning, because it no longer describes anything. Paging does not. That is the only case where the two differ, which is why page changes are handled separately from filter changes.
    The header box is a real <input type="checkbox"> with indeterminate set from script - it is a property, not an attribute, and cannot be written in markup. Assistive technology reports "mixed" only for a genuine checkbox; a styled div announces nothing.
    Its accessible name states the scope - "Select all 25 orders on this page" when empty or dashed, "Clear the 25 selected orders" when ticked, updated when the page size changes. "Select all" alone is the ambiguity this section exists to remove.
    Destructive bulk actions restate the number and the noun in the dialog: "Delete 128 orders?". A count that arrived from a filter-wide selection is the one a user is most likely to have misread.
    Ordering by hand
    The handle is always visible at #c3c1b8 - not revealed on hover. A reorder affordance that only appears under the cursor is invisible on touch and invisible to anyone scanning for it.
    Handle darkens to #57564f, row takes the standard #f0efe9 hover, cursor is grab. The whole row is the drop target; only the handle starts a drag, so a click anywhere else still opens the line.
    The dragged row lifts out - white, carrying the menu shadow --shadow-menu 0 6px 16px rgba(27,26,23,0.08) (not a shadow of its own), a 0.6° tilt, following the pointer, above the rows it crosses. With reduced motion it lifts without the tilt. A 2px #1d4d33 line marks where it lands, and the rows below shift down by its height over 150ms. The row it left behind is removed, not greyed: the list you see is the list you will get.
    Tab reaches the handle. Space or Enter picks the row up, ↑ ↓ move it one place per press, Space drops it, Esc returns it. Each move announces the new position in a live region - without it a screen-reader user has moved something and been told nothing.
    Identical mechanics, different payload. Statuses save on drop because the card is its own save scope; item lines mark the order dirty and wait for the sticky bar.
    The handle widens to 24px and the row to 48px, per 15b. Dragging starts on touch-and-hold, 200ms - an immediate drag would steal every scroll gesture that began on a handle. A short haptic tick marks the pickup.
    Every value here is an existing token. Handle #c3c1b8, handle hover #57564f, row hover #f0efe9, picked-up row #e7efe8 (the selected-row tint), insertion line #1d4d33, lift shadow --shadow-menu 0 6px 16px rgba(27,26,23,0.08). Nothing about dragging needs a colour of its own - if a drag state seems to want one, the state is being made to carry meaning that belongs to the insertion line or the shadow.
    One component, however many lists. A host differs only in what a row renders and when the change commits: inside a form the reorder marks it dirty and waits for that form's save; in a card or panel that owns its own save it commits on drop. A second drag implementation is where the keyboard path gets dropped. A second drag implementation is where the keyboard path gets dropped.
    Only the handle initiates. Dragging from anywhere else in the row would make text selection impossible and would fight the click that opens the line (16b). The whole row is still a valid drop target.
    A 4px threshold before a drag begins. Without it, a slightly imprecise click on the handle registers as a zero-distance drag and the row appears to jump.
    Move the row, do not clone it. Rendering a ghost in the old position alongside the lifted row shows the list in a state it will never be in, and the insertion line then has two things to disambiguate.
    Animate transform, not layout. Rows shift with transform: translateY over 150ms; animating height or margin on a long list drops frames on exactly the lists that need reordering.
    Under prefers-reduced-motion the shift is instant and the tilt is dropped. The insertion line and the shadow stay - they carry the information; the motion is decoration.
    Dropping in the same place is not a change. No dirty flag, no save, no toast. A user who picks a row up and puts it back has done nothing.
    A failed save restores the previous order and says so. An optimistic reorder that silently reverts on the next load is worse than one that never appeared to work.

    Uses
    One name per message, and three messages exist. .sp-field__help is a hint that is always true and stays when the value is right. The same element takes data-color="warning" for something the user may pass - a future date, a limit below the average - and the input takes the colour with it. data-color="success" is a value that checked out. data-color="danger" is a problem that blocks the save, bound to its input with aria-describedby, and the input takes the colour with it. One class and one attribute, never a separate class per colour: the class carries the slot and the quiet grey, the attribute carries only the colour and the weight.
    A warning is not a failed validation. The field takes data-color="warning" but never aria-invalid, because nothing is wrong - the value is allowed and the save proceeds. Use it where the value is unusual enough that a user would want to know they meant it: a date in the future, a name close to an existing one, a limit below what the category has averaged. If the save cannot proceed it is an error, and if the user can do nothing about it, it is not a message at all.

    Label, control, and optionally: an error message, and any of three slots the field itself owns rather than any one field type - a leading icon, a trailing unit as text, and a trailing button.     Fixed
    RangeInput is a 4px --line rail spanning the field's full width, with the handles travelling inside it so that at either bound a handle's edge lines up with the field's edge - and with the entry field beneath it - rather than hanging over: the chosen span is --green, each handle a 14px --surface circle with a 2px --green border carrying role="slider" and its real value. With entry, the two fields sit beneath at --sp-8, each half the width. On touch the rail keeps its 4px but the handle grows to 18px and carries an invisible --control-h-touch target around it, so it is grabbable without the rail thickening. The snap is declared on the rail as data-step, so the values a drag can land on are the ones the page allows and nothing between them: a value stepping by 100 never produces 16.473. Left undeclared it snaps to a hundredth of its own span, so a rail is never smoother than it is wide. Opening positions arrive as data-at percentages with the span as data-span, each matched by its own rule; from then on a drag writes the live percentage onto the handle, since a value the user is moving cannot exist in the stylesheet. Height --control-h, radius --r-field, padding --sp-12, border --line-3, gap --sp-6 to the label. The slots sit inside that box: a leading icon --sp-12 from the left in --ink-5, taking no pointer, a unit --sp-12 from the right, a trailing button --field-trail square inset --sp-6 so it clears the border on every side. Each is absolutely placed and the input reserves its room instead, so the value never runs under one: the padding is the slot's own inset plus its width plus --sp-8, which puts the text 8px past the icon rather than a fixed distance from the edge. The placeholder sits in that same box, so it starts exactly where a typed value would. A NumberField is tabular with its unit stated inside the field, so the user never types it and the figures still read down a column. The unit is the field's, not the component's: currency, a count, a percentage or nothing at all. Constraints live on the element - min, max, step, maxlength, required, pattern - and the browser validates before any script. A field fills the width it is given. See c5 for the panel and both modes. TokenField is the same field - --line-3 border, --r-field, --control-h as a minimum height so an empty one matches every other field - with its values wrapping inside at 6px as chips (c6) and the input taking the remaining width. It grows in height as values wrap; it never scrolls sideways.
    A date field on iOS sits like every other field. Tapping still opens the native picker. All of this shows only in WebKit: a drawing or a check made in Chromium looks right either way, so check a date field in WebKit with the iPhone 15 profile. Blink and Gecko already behave, so nothing changes there.
