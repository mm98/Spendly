17a Images and files — upload, replace, delete
Four places in the app take a file, and they behave the same way underneath. Written out because the obvious shortcuts here are all wrong in ways that lose the user's file — and a lost receipt is the one thing this product cannot do.
THE FOUR PLACES, ONE MECHANISM
Item photo (one per line, 1b) · order attachments (many, 1a) · receipt scan (one, feeds 3a) · avatar (one, 11a). All four are the same FileDrop component with different accept, multiple and compact settings. Do not write four uploaders.
THE LIFECYCLE — AND THE THREE SHORTCUTS TO AVOID
UPLOAD, STEP BY STEP
1
Validate before anything leaves the browser. Type by extension and sniffed magic bytes, then size. A rejection renders inline on the zone, which stays usable — never a dialog, never a toast, and never a silently ignored drop.
2
Show the tile immediately, from a local object URL, before the network is touched. The user sees their file in place within one frame; the progress ring is drawn over that preview, not over a grey box.
3
Upload to staging, get an id. The file goes to storage straight away and returns an id. The order draft holds the id — nothing is attached to a record yet.
4
Server derives what it needs — EXIF-corrected orientation, a stripped copy without GPS and camera metadata, a thumbnail, and for PDFs a first-page render. HEIC is converted for display; the original is kept as uploaded.
5
Saving the order commits the ids. Files uploaded to a draft that is never saved become orphans, cleaned by a job after 24 hours. That window is deliberate: it is what makes step 3 safe.
REPLACE — NOT A DELETE FOLLOWED BY AN UPLOAD
Replace uploads the new file first, then swaps the reference, then releases the old one. If the upload fails, the old image is still there and the tile says the replace failed. Deleting first and uploading second means a failed upload leaves the user with nothing — from an action that was never destructive.
During a replace the tile shows the old image dimmed with the progress ring over it, not an empty slot. The user should be able to abandon the page mid-replace and still have their original.
DELETE
An item photo the user added: removes at once, toast + Undo, no dialog. An item photo or attachment that came from a scan: confirms first, because it is evidence the user did not create and cannot re-take. Deleting the order: the dialog names the attachment count, so the receipts are never a silent casualty.
Removing a file from a draft only drops the id; storage cleanup is the same 24-hour job. Undo therefore always works, because nothing was actually deleted yet.
THE THREE SHORTCUTS, AND WHY EACH FAILS
Uploading on save instead of on drop. Tempting, because then the draft is self-contained. But a 12 MB receipt over hotel wifi turns Save into a thirty-second freeze with no feedback, and a failure there loses the whole form — not just the file.
Attaching straight to the record on drop. Writes to an order the user may abandon, and means an unsaved order already has state on the server. The staged-id approach gets the immediate upload without the write.
Replace as delete-then-upload. Turns a non-destructive action into a destructive one whenever the network hiccups. Always upload, swap, release.
And a fourth: reusing the browser's file input styling. Every one of these is the same FileDrop component — the hidden input is an implementation detail, and the drop target, the keyboard focus ring and the per-file error rows are the design.

Failure is per file, never per batch. Drop five and one is rejected: four upload, the fifth keeps its tile with the reason and a Remove. Nothing rolls back the good ones.
The reason is specific — "Too large", "Not a supported type", "Upload failed" — because "Error" tells the user nothing about whether to retry or pick a different file.
Attachments have no replace, only add and delete. A receipt is evidence of one purchase; swapping the file behind an unchanged filename is how a record starts lying. Item photos do replace, because a photo is illustration.
ALSO TRUE EVERYWHERE
Navigating away mid-upload. The prompt counts uploads in flight ("2 files are still uploading"), because leaving loses them and the sticky-save prompt alone does not mention files.
Duplicate file on one order. Same name and size, warned not blocked, same as the duplicate-name pattern in 16c — two photos of one item are legitimate.
On dark (12a): every thumbnail keeps a 1px #463f37 border and renders at 90% opacity, or a white receipt scan floats as a bright edgeless rectangle. Full opacity returns on hover and in the viewer.
The source menu adapts, it does not branch. Same component everywhere: Take a photo is present only where a camera exists — on desktop it is absent, not disabled. Use the receipt appears only when the order has an attachment, and opens a page picker so a crop of the receipt can become the item photo. With one source available the menu is skipped and the picker opens directly, because a one-item menu is a wasted tap — which is why on desktop, with no camera and no attachment, clicking the slot opens the file picker with no menu at all.
One picker entry, not two. "Choose a photo" and "Choose a document" would be the same file dialog on desktop, and the item photo accepts images only — so there is no document entry here. On mobile the single entry opens the photo library, since that is where a photo of a chair is. The attachment strip is the opposite case: it accepts PDFs, so its menu's picker entry opens the file browser instead. The accept list decides which, not a second menu row.
Never a full-screen blocking overlay for an upload. The progress belongs on the tile; the rest of the form stays editable throughout.
