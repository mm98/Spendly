17a Images and files - upload, replace, delete
Five places in the app take a file, and they behave the same way underneath. Written out because the obvious shortcuts here are all wrong in ways that lose the user's file - and a lost receipt is the one thing this product cannot do.
The five places, one mechanism
Item photo (one per line, 1b) · order attachments (many, 1a) · receipt scan (one, feeds 3a) · avatar (one, 11a) · vendor image (one per vendor, 5b, 5c, specified in 17e). All five are the same FileDrop component with different accept, multiple and compact settings. Do not write five uploaders.
THE LIFECYCLE - AND THE THREE SHORTCUTS TO AVOID
UPLOAD, STEP BY STEP
1
Validate before anything leaves the browser. Type by extension and sniffed magic bytes, then size. A rejection renders inline on the zone, which stays usable - never a dialog, never a toast, and never a silently ignored drop.
2
Show the tile immediately, from a local object URL, before the network is touched. The user sees their file in place within one frame; the progress ring is drawn over that preview, not over a grey box.
3
Upload to staging, get an id. The file goes to storage straight away and returns an id. The order draft holds the id - nothing is attached to a record yet.
4
Server derives what it needs - orientation applied to the pixels, then everything that can track the person or name their device removed: GPS, camera make, model and serial, lens, software, owner and artist names, dates and times, maker notes, XMP, IPTC, comments, and any colour profile other than sRGB or Display P3. Then the renditions below. The original is never kept. A picture filed on the order itself (a receipt, a scanned page) also keeps one full-size copy in its own format, cleaned the same way, for Download and zoom. A line's photo and the vendor image keep only their renditions. A PDF is kept exactly as uploaded, with a first-page render for its renditions. A file the app cannot open is refused, never stored; its tile says "Not a supported type".
5
Saving the order commits the ids. Files uploaded to a draft that is never saved become orphans, cleaned by a job after 24 hours. That window is deliberate: it is what makes step 3 safe.
REPLACE - NOT A DELETE FOLLOWED BY AN UPLOAD
Replace uploads the new file first, then swaps the reference, then releases the old one. If the upload fails, the old image is still there and the tile says the replace failed. Deleting first and uploading second means a failed upload leaves the user with nothing - from an action that was never destructive.
During a replace the tile shows the old image dimmed with the progress ring over it, not an empty slot. The user should be able to abandon the page mid-replace and still have their original.
DELETE
An item photo the user added: removes at once, toast + Undo, no dialog. An item photo or attachment that came from a scan: confirms first, because it is evidence the user did not create and cannot re-take. Deleting the order: the dialog names the attachment count, so the receipts are never a silent casualty.
Removing a file from a draft only drops the id; storage cleanup is the same 24-hour job. Undo therefore always works, because nothing was actually deleted yet.
The three shortcuts, and why each fails
Uploading on save instead of on drop. Tempting, because then the draft is self-contained. But a 12 MB receipt over hotel wifi turns Save into a thirty-second freeze with no feedback, and a failure there loses the whole form - not just the file.
Attaching straight to the record on drop. Writes to an order the user may abandon, and means an unsaved order already has state on the server. The staged-id approach gets the immediate upload without the write.
Replace as delete-then-upload. Turns a non-destructive action into a destructive one whenever the network hiccups. Always upload, swap, release.
And a fourth: reusing the browser's file input styling. Every one of these is the same FileDrop component - the hidden input is an implementation detail, and the drop target, the keyboard focus ring and the per-file error rows are the design.
Rendition Size Serves How it is made
square-256 256 x 256 Every small square: --mark-medium 42 (the order row, the item line, a bookmark row) and --mark-large 64 (the form slot), at up to 3x; the account picture; the file tile on an order. The browser scales it down for the 42px slot. Cut around the subject (the strongest colour, contrast and skin tones).
wide-1080 1080 px wide Every larger view: the card photo band (2c) at up to 3x, the vendor image filling the band, the bookmark card strip, and the image viewer (12b) fitted. Aspect kept; the band and strip crop it with cover, centred; the viewer fits it.
full-size As uploaded An order's own picture only (a receipt, a scanned page): Download, and zoom in the viewer past wide-1080. Upload's own format, cleaned as step 4. Not made for a line's photo, the vendor image or a bookmark.
Renditions - one set for every picture
Two renditions, the same everywhere, one resize job: item photos, the vendor image (17e), bookmark pictures, the account picture, and the files on an order (a PDF from its first-page render). Both are WebP, quality 85, alpha kept, never upscaled - an image smaller than a rendition is stored at its own size. The only third copy is the full-size one of an order's own picture. Each extra size is stored for every picture, so a new slot uses one of these two rather than adding a size.
The subject cut on square-256 is a guess. The server centres the square on the part with the strongest colour, contrast and skin tones. A busy background, or a large logo on a receipt, can pull the square away from what matters. It has not been tested on real product photos yet. The wide copy is not cut this way: the band and strip stay centred, since centring them on the subject would need a stored focus point for each picture. That is not built.
Serve with srcset over the renditions that fit the slot, width descriptors and sizes set to the slot's CSS size, so the browser picks by pixel density. Renditions are immutable and addressed by content hash: they cache forever, and a replace changes the URL.
17b Every state, drawn
The item photo slot and the attachment strip, in each state they can be in. A control shipped without its error state gets that state invented later, differently.
Item photo - the form slot
Empty. Click opens the file picker. Drop works without it. Keyboard-focusable with the standard ring.
Filled, at rest. No controls visible. Clicking opens the viewer (12b).
Open for editing. The slot names what it holds along its foot and takes Remove beneath it. Replace is the label itself - the whole face is the file input, so there is no second control to hit.
Uploading, or replacing. The ring sits over the image - the old one during a replace, the new local preview during a first upload. Never an empty box.
Failed
Failed. The slot keeps the failure and offers retry - it does not revert to empty, which would read as if nothing had happened.

Also true everywhere
Failure is per file, never per batch. Drop five and one is rejected: four upload, the fifth keeps its tile with the reason and a Remove. Nothing rolls back the good ones.
The reason is specific - "Too large", "Not a supported type", "Upload failed" - because "Error" tells the user nothing about whether to retry or pick a different file.
Attachments have no replace, only add and delete. A receipt is evidence of one purchase; swapping the file behind an unchanged filename is how a record starts lying. Item photos do replace, because a photo is illustration.
Navigating away mid-upload. The prompt counts uploads in flight ("2 files are still uploading"), because leaving loses them and the sticky-save prompt alone does not mention files.
Duplicate file on one order. Same name and size, warned not blocked, same as the duplicate-name warning on the create and rename fields in 5b and 5c - two photos of one item are legitimate.
On dark (12a): every thumbnail keeps a 1px --line-3 border and renders at 90% opacity, or a white receipt scan floats as a bright edgeless rectangle. Full opacity returns on hover and in the viewer.
On light, thumbnails are toned; full-size images are not. A product photo carries whatever colour the vendor's studio used, and a grid of them fights a palette built on muted greige and one capped chroma. Every thumbnail therefore renders filter: saturate(0.88) under a warm scrim of rgba(236, 234, 228, 0.08). Enough to pull unrelated photos toward the same temperature, not enough to look filtered - a washed-out photo of a user's own purchase reads as a bug, which is the failure mode to avoid.
On dark there is no scrim. The 90% opacity above already does the same job from the other direction, and a warm light scrim over a thumbnail on the dark --bg would lighten it - working directly against the glare reduction it sits beside. Saturation is left alone too: against a dark surface a photo already reads less saturated than it does on white. One treatment per theme, and they do not compose.
The viewer removes the treatment entirely. Full size is where you inspect the actual thing, so it renders at full fidelity against the dark overlay. The tone belongs to the grid, not to the image.
Tune the two numbers against real photos before shipping. They are a starting point set against placeholders. Judge them on a row of five thumbnails from five different vendors - the test is whether the row reads as one surface, not whether any single photo looks good.
The platform owns the picker. The slot is a file input, so the camera and the photo library come from the operating system - on a phone the native sheet, on a desktop the file dialog. There is no source menu of our own: clicking the slot opens the picker, and dropping a file bypasses it.
One picker entry, not two. "Choose a photo" and "Choose a document" would be the same file dialog on desktop, and the item photo accepts images only - so there is no document entry here. On mobile the single entry opens the photo library, since that is where a photo of a chair is. The attachment strip is the opposite case: it accepts PDFs, so its menu's picker entry opens the file browser instead. The accept list decides which, not a second menu row.
Never a full-screen blocking overlay for an upload. The progress belongs on the tile; the rest of the form stays editable throughout.
17c Thumbnails in a list row
Four states, one width. The mark is the same square on every row whether it holds a photo, the vendor's image, nothing, or a photo and a count - the count sits inside it - so the text beside it always starts at the same x.
The four states
One photo The first item's photo, object-fit: cover, at the row mark's own size and radius.
+7 More than one Same square, with the remaining count as a badge inside its corner.
No item photo, vendor has an image The vendor's image, drawn exactly as an item photo, faded.
No photo, no vendor image The empty mark - dashed, with the image symbol in --ink-6 and no label.
Why the width is fixed
One width whether or not there is a photo, and whether or not there is a count. A cell that sizes to its content moves the vendor name a few pixels per row, which is the same defect the fixed vendor column exists to prevent - the eye has to re-find the name on every line.
The count is .sp-mark__count, a badge inside the mark's own corner rather than a sibling beside it - which is what keeps the width constant. A five-digit count is the only thing that could overflow it, so cap the display at +99.
Notes for implementation
The diagonal hatch is not a state. It is how these mockups draw a photo they do not have. Wherever it appears, a real image renders. Only the dashed square is literal.
No stacked pairs, no ring, no second image. An earlier draft stacked two squares with a white ring and switched to a badge past two - three treatments for one idea, and the column read as inconsistent. One square plus a count is the whole rule.
The count is photos; the paperclip is attachments. They can disagree - four item photos and no receipt, or a receipt and no photos. Never derive one from the other.
On a cancelled row the thumbnail dims with the rest of the cells at opacity 0.6. It is not a fifth state.
Order of precedence: the first item line with a photo, then the vendor's image in the same .sp-mark--photo with .sp-mark--faded, then .sp-mark--empty. Resolved at render from the order's lines and its vendor - nothing is stored on the order (17e).

Notes for implementation
Every hatched block in these files is one of these nine. The hatch pattern carries no meaning beyond "an image belongs here" - match the position to this table rather than inferring intent from the placeholder's size or colour.
Two things are photos of goods; two are photos of paper. Item photo and card strip show what was bought. Attachment tile and receipt preview show the document proving it. They are separate fields on separate models and must not share a picker, a viewer entry point, or a count.
Every fallback is a mark, never a broken-image glyph or a grey box with a mountain icon. Either the IdentityMark (order thumbnail, card strip, avatar, vendor) or nothing at all (attachment strip, page rail). The vendor image fallback is drawn as an item photo, faded. An empty tile appears in exactly one position - the item photo - because a list of item lines is where a missing photo is genuinely unremarkable.
Squares are cut around the subject; the card band and bookmark strip crop the wide copy with cover, centred. The receipt preview and page thumbnails are the exception: they letterbox at page aspect because cropping a receipt can hide the total.
The tone from above applies to the first four positions only. Goods get toned; paper does not, and neither does anything in the viewer - those exist to be read.
17e Vendor image - validation, renditions, where it shows
One optional image per vendor, uploaded in 5b and 5c. It can be the vendor's logo, its shop, or any picture the user connects with it. It has one use: on any of that vendor's orders where no item line has a photo, it is shown in place of the item photo, drawn exactly as one and faded.

Renditions
The same set and the same resize job as an item photo (17a), since it stands in for one in the same places. It uses square-256 in the order row and the form slot, and wide-1080 filling the card band. It keeps no original and no full-size copy - only these two.
Notes for implementation
Lifecycle is 17a, unchanged. Validate in the browser, show the local preview, upload to staging for an id, save commits it, orphans are cleaned after 24 hours. Replace is upload, swap, release. Remove has no confirmation, since the user added it; it only drops the id until save.
Processing on the server, in order: sniff type; for SVG, sanitise (strip scripts, event handlers, external references and foreignObject) and rasterise to PNG at 1024 px - an SVG is never served as SVG; apply EXIF orientation and strip all metadata as 17a step 4; take the first frame of an animated WebP; check the smallest and largest rules; write the two renditions of 17a. Nothing else is kept.
Data model: vendor.image_file_id, nullable. Nothing is stored on orders. An order's thumbnail is resolved at render: first item line with a photo, else the vendor's image faded, else the empty mark. Changing or removing a vendor's image therefore changes every one of its orders at once.
Drawn as an item photo, faded. That is the only difference. Same component, same crop, same tone, same click as an item photo in that spot, plus .sp-mark--faded on the row mark or .sp-record__photo--faded on the band photo: filter: opacity(var(--photo-fallback-opacity)), 0.6. A filter rather than opacity, so it compounds with the void row's own 0.6 instead of replacing it. The fade tells the user the picture belongs to the vendor, not to this order. Data: the order's photo count and the No photos filter count item photos only.
Vendor lifecycle. Archive keeps the image. Delete releases it. Merge (5j) keeps the target's image; if the target has none, the source's moves to it. Duplicating an order (8a) does not touch it - the image belongs to the vendor.
Open question - dark mode, not designed yet. A vendor image with transparent areas (a cut-out logo, a PNG with no background) sits on --surface-2. In the light theme that ground is pale, so a dark logo reads. In the dark theme it is dark, and a dark logo on it can disappear, The same applies to item photos with transparency, though they are rarer. How often this happens and how bad it looks is unknown: these mockups only draw the hatch stand-in, and no real images have been tried against the dark surface.
This needs implementation and testing before it can be designed. Build the vendor image as specified above, then test real images in the dark theme: dark logos on transparency, light logos on transparency, and ordinary photos, in the form slot, the order row and the card band. Until then, the dark theme shows the image on --surface-2 exactly as the light theme does, and nothing is added for it - no light ground, no outline, no detection of transparent images. The result of the test decides the design; it is not decided here.
