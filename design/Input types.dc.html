14a Input types
Every control used across the set, with its states and what is specific about it here. This is the whole vocabulary — a screen needing something that isn't on this page is a signal to reconsider the screen.
NOTES FOR IMPLEMENTATION
One box, everywhere. Every text-entry and select control is 1px solid #dedcd4, radius 9px, padding 10px 12px, text 14px — landing at 42px tall. Controls that aren't text, like the stepper, get that height explicitly rather than sized by content, so a row of mixed controls needs no alignment work.
Focus is one treatment — border #1d4d33 plus a 3px rgba(29,77,51,0.12) ring, on every focusable control including toggles, checkboxes and drop zones.
Labels always visible — 12px/600 above the control. No floating labels, no placeholder-as-label: both lose the label when the user is typing and needs it.
Which side an icon sits on is a rule, not a choice. Left says what the field holds — the search glyph, a currency prefix, a category's IdentityMark. Right says what clicking does — the combobox chevron, and the calendar that opens a date picker. A date field therefore carries its calendar on the right, in the same place as the chevron, because it does the same kind of thing.
Validation on blur once touched, and on submit. Never per keystroke. An error clears on the next valid blur, not the first character typed.
Touch — 42px is under the 44px minimum, so on mobile vertical padding goes to 12px and every control's row carries 44px of hit area.

The target is 44px, the square is 18px. A checkbox is the smallest control in the set and almost always sits inside something else clickable — a list row that navigates, a facet row that filters. A 18px target means a near-miss does the other thing: on the order list it opens the order instead of selecting it, and on touch that is the common case, not the edge. The square stays 18px; the hit area is the cell it lives in, stretched to the row's full height and padded out to 44px (44px on touch), and that cell calls stopPropagation so a hit anywhere in it never reaches the row.
A labelled checkbox is not the problem; a bare one is. Where the label belongs to the checkbox — facet rows, settings toggles, the options in a Set status popover — the label is the target, so the square, its text and its count all toggle and the real hit area is already the width of the row. The problem case is a checkbox whose neighbouring text belongs to something else: in a table row the vendor name opens the order, so the checkbox has no label of its own and the bare square is all there is. That is the one that needs a padded cell and stopPropagation. The test is not "table or facet" — it is whether the text beside the checkbox does the same thing the checkbox does.
Checkbox filters, toggle switches behaviour. A checkbox belongs to a set you are narrowing; a toggle turns one thing on. Never mix them in one group.
A toggle applies immediately and never has a Save. If a setting needs a save, it is not a toggle.
Indeterminate is a real third state, shown as a dash, used by "select all" over a partial selection. Clicking it selects all.

The seven picker colours aren't a selection of nice greens — they sit on a rule, and the rule is what lets an eighth be added without a designer. Values are OKLCH, because the rule is only visible in a perceptual space: in hex these look arbitrary, in OKLCH they line up.

The neutrals are the quiet part of the system: they sit on the amber hue at almost no chroma. That is why the canvas reads as warm greige rather than grey, and why a true grey dropped in anywhere looks dirty beside it.

Lightness climbs in even perceptual steps and chroma drops with it. That is the whole ramp: a light colour in this system is never as saturated as a dark one. Hold chroma flat while lightening and the pale end turns to mint — the single most common way a palette like this gets broken.
3 — Chroma is capped
Nothing in the app exceeds C 0.12, and that ceiling belongs to one colour — the amber marker at #b58a2b, which has to read as a 2px hairline. Picker swatches stop at C 0.08. This is why the interface never looks like a dashboard: saturation is spent on a single marker rather than distributed across every chart.
ADDING AN EIGHTH PICKER COLOUR
1
Pick the hue: an existing family, or a new one at least 40° from all four. Anything closer reads as a mistake rather than a distinction.
2
Set lightness in L 69–86, the band the existing swatches occupy, and keep at least 5 L from every swatch on the same hue — closer than that and the two are indistinguishable in a 12px chip.
3
Derive chroma from that lightness rather than choosing it by eye: roughly 0.08 at L 70, 0.05 at L 80, 0.025 at L 86. Never above 0.08.
4
Check the four places it lands: a 26px icon tile with a white glyph, the same tile with dark ink (above L 75 the glyph flips), a 12px chart bar between its neighbours, and a filter chip.
5
Add the dark-theme pair in the same commit. Dark lifts L by about +18 and holds chroma; a swatch without its pair only works in one theme.

WHAT NOT TO DO
Don't open a free colour picker to users. Every swatch has to survive four contexts and a second theme, and a hex chosen from a wheel satisfies none of them — this is decision 5b in the design, not a limitation to be relaxed later.
Don't add a colour to distinguish two things that a label already distinguishes. Twelve categories don't need twelve colours; the top five plus "other" is what the charts show, and that is deliberate.
Don't interpolate in hex or HSL when generating variants. HSL lightness is not perceptual, and the midpoints come out muddy — the whole reason this page is written in OKLCH.
14d Component API — the options each control needs
What each control must accept to serve every place it is used in this design, and nothing beyond that. Nineteen components. The right-hand column names what drives each option, so an option with nothing behind it can be cut.
NOTES FOR IMPLEMENTATION
Every control takes the same five: label, value, onChange, error, disabled — plus id, name and required passed through. Don't re-declare them per component. One shared field wrapper owns the label, the error message and the spacing; each control renders only its own box.
Controlled only. No internal value state, no defaultValue. The order draft is the single source of truth — a control keeping its own copy is how a field silently disagrees with what gets saved.
No variant="danger" on an input. Error is a boolean plus a message, never a visual variant, which makes the red state impossible to apply for decoration.
Resist the extra option. Each row is short on purpose. When a screen needs something not listed, add it here first — that review step is what keeps this at seventeen components rather than forty.

Error and hint share one slot so a field never grows when it fails — the row height is identical in both states, which is what stops a form jumping as you tab through it.
WHAT IS NOT A COMPONENT HERE
Radio group with two options. Two mutually exclusive choices are a Segmented, always. Radio starts at three, and only when the options carry meta or wrap — otherwise Segmented still wins.
A standalone slider. The one range control is the amount facet, and it is a RangeSlider paired with two AmountFields — see 14e. A slider alone is never enough, because a receipt total is usually typed.
Autocomplete, tag input, rich text, native select. All are the Combobox, the Chip list, the multiline TextField, or nothing. Each would be a second implementation of something already here, and the second one is always the one that misses the keyboard support.
Form. No form component. Screens compose the wrapper and the controls directly, because each screen's save behaviour differs — per card in Settings, one sticky bar on order edit, a staged dry run in import.
BUILD ORDER
1. The field wrapper, then TextField (PasswordField is the same field plus a reveal) and Button — between them they unblock every screen.
2. Combobox. The largest piece by a distance, and four screens are waiting on it. Do the keyboard table in 14a before the styling, not after.
3. AmountField and Stepper, together — they share the parsing and formatting.
4. Checkbox, Segmented, Chip, SearchInput. Small, and the order list needs all four at once.
5. IdentityMark, SortControl and Pager — small, and the vendors library and order list need all three.
6. FileDrop, DateField, SwatchPicker, Toggle.
7. RangeSlider, last — it is used once, in the amount facet, and only alongside the AmountFields from step 3.
Each one lands with its states from this page as the acceptance criteria — default, filled, focus, error, read-only, disabled, loading where it applies. A control shipped without its error state gets that state invented three times later, differently.

NOTES FOR IMPLEMENTATION
The track is inset by half a thumb, not flush. margin: 0 9px — half of the 18px thumb. The thumb is positioned by its centre, so a track running the container's full width puts the thumb 9px outside it at 0% and at 100%. Inset the track and the thumb's outer edge lands exactly on the container edge, level with the two amount fields below.
The 9px is derived, not chosen: 14px + 2px border × 2 = 18px, halved. Change the thumb size and this number changes with it. Same reasoning as the overlay-inset rule in 15a — the number comes from the thing it must align with.
Slider and fields are one control, two views. Dragging updates the fields live; typing moves the handles on blur. Neither is a mirror of the other — both write the same pair of values.
The bounds come from the data, not a constant. "0 — 25.000 kr." is the account's own range, rounded up to a sensible step, and it moves as orders are added.
The fields are the accurate path. Handles snap to a step proportional to the range; typed values do not. This is why the slider alone is not enough — 3.000 exactly is typed, not dragged to.
Handles cannot cross. Each stops at the other; they do not swap. Two handles at one position stay draggable — the one last moved keeps priority.
Filtering is debounced 300ms after the last change, whichever input caused it. A drag does not fire a request per pixel.
Each handle is a real slider input with its own aria-label ("Minimum amount"), arrow-key stepping, and Home/End. A pair of divs with a drag handler is not reachable by keyboard.
On touch the handles grow to 24px hit areas without changing their painted size.

The 28px avatar in early sidebar drafts was 12px type at 2.3× and read as cramped, which is why the sidebar mark is 32px.
Colour is deterministic, from a fixed list. Hash the normalised name to an index into the seven picker swatches from 14c. Same vendor, same colour, on every screen and after every reload — a mark that changes colour is worse than no mark. Derive from the canonical name, never an alias (5d), or one vendor gets two marks.
Never a random or generated colour. The seven swatches are the whole range, for the reasons in 14c. A hash into an HSL wheel produces colours outside the palette on the first vendor it meets.
Ink flips above L 75, the same threshold as the category tile — light fills take #1b1a17 or the family's dark tone, not white.
The mark is decoration, not information. It always sits beside the name it belongs to and carries aria-hidden; nothing is identified by colour alone.
No logos, ever. No favicon fetching, no upload. A receipt tracker that reaches out to a vendor's website to render a list row is a privacy leak and a broken row when it fails.

Yes — the vendors library (5a). Forty-two rows of one kind, scanned to find one. The mark is the fastest way in.
Yes — the command palette (9d) and any combobox listing vendors, where rows are dense and homogeneous.
Yes — order cards (2c) and the order detail rail, where there is room and one vendor to identify.
No — order list rows (2b). The vendor column is 200px and already first, fixed and left-aligned; a 26px mark plus its gap takes a sixth of it to repeat what the text beside it says. The column exists to be scanned as text.
No — mobile order rows (7a). Same reasoning, less room. Fields were removed to make those rows readable; a decorative mark does not earn the space back.

NOTES FOR IMPLEMENTATION
A photo thumbnail always carries a 1px border. #e6e4dc on light, #463f37 on dark, inset with box-sizing: border-box so it comes out of the declared size rather than growing it. Product photography is overwhelmingly shot on white, so without a border a pale photo has no edge against a white row or card and the cell reads as empty rather than as an image. This is the same reason 12a keeps a border on every thumbnail in dark mode — the difference is only which colour, not whether.
One positioner, every overlay. Combobox panel, row and card menus, submenus, date picker, account menu. Six implementations of "open below the thing" is six places for an off-screen panel to appear, and the one that gets it wrong is always the one on the last row of a long list.
Decide once, at open. Measure the trigger, measure the panel's natural height, compare against space above and below, then place it. Do not re-measure on scroll — a panel that drifts or re-flips while the user is reaching for an item is worse than one placed imperfectly. Scrolling the container closes the overlay instead.
Render at document level, not inside the row. The list column is a scroll container with overflow: auto (9a), so a panel that is a DOM child of a row is clipped by it. Portal it out and position it with fixed coordinates.
Vertical flips, horizontal shifts. Flipping sideways moves a menu away from the row it acts on and, in a table, over a different row's content. Shift and clamp instead, keeping 8px clear of the viewport.
The chevron reports the decision. A trigger whose glyph always points down is lying half the time. On a combobox the chevron flips with the panel; on a submenu parent it points at the side the submenu opened on.
Announcement — combobox. The trigger is role="combobox" with aria-expanded, aria-controls pointing at the panel, and aria-activedescendant naming the highlighted option. Focus stays in the input; the panel is role="listbox", each group a role="group" with aria-labelledby on its header, each option role="option" with aria-selected. The filter result count goes to a polite live region — "6 vendors" — because a sighted user sees the list shrink and a screen-reader user is told nothing otherwise.
Announcement — menu. The trigger is aria-haspopup="menu" with aria-expanded, and it needs an aria-label naming its subject, not its shape: "Actions for order SPENDLY-447", never "More". Fourteen buttons all labelled "More" is a list a screen-reader user cannot navigate. The panel is role="menu", items role="menuitem", a submenu parent aria-haspopup="menu" and aria-expanded on itself. Unlike the combobox, focus moves into the menu — first item on Enter or ↓, last item on ↑.
Both: Esc closes and returns focus to the trigger, always. Click outside closes without acting. The overlay is the topmost Esc target (9a), so an open panel inside a dialog takes Esc first. Nothing outside is aria-hidden — these are not modal, and a menu that hides the page from assistive tech while the page is still visible is lying about its own modality.
Reduced motion. The panel appears without the 8px translate; opacity only. Nothing about placement changes.
