15a Columns, rows, and what goes full width
Which controls carry an icon, and which do not. Search has a leading magnifier — it is the one control whose purpose is not obvious from an empty field. Create has a leading plus, and keeps it at every width because the plus alone is what the button becomes when the label goes. Sort and any filter control carry a trailing chevron and nothing leading: the word "Sort" and the filter's own name already say what they are, and a leading glyph on each turns the toolbar into a row of competing marks. A segmented control never carries an icon — its labels are the whole control.
Leading means what it is, trailing means what it does — the same rule as the fields in 14a. The magnifier and the plus describe the control; the chevron says a panel will open. Never both on one control.
Every screen in the set uses one of four column shapes, and every field is either full width or a fraction for a reason that can be stated. Written down here because it was consistent across the designs but never explicit — and an undocumented grid is the first thing to drift.
THE ONE RULE BEHIND ALL OF IT
One fluid column per layout. Everything else is a fixed pixel width. The main column takes 1fr; rails, navs and facet columns are fixed. Two fluid columns means neither has a predictable width, so nothing inside either can be sized with confidence — and the first long vendor name changes the whole page.
Gaps, not margins. 24px between columns, 14px between stacked cards, 16px in a card grid, 12px between fields. Set on the container, never per child, so reordering and deleting stay safe.
An overlay's inset is never a free number. A control positioned over something — a checkbox on a card, a badge on a thumbnail, a PDF tag on an attachment tile — is inset by the padding of whatever it must line up with, not by whatever looks about right. A card's checkbox sits 16px in because the bulk bar above it has 16px padding, so the two checkboxes share an x. Pick the element it aligns against first, read its padding, use that number.
A number never gets a fixed-width box. Counts, badges and totals change length with the data — 3 today, 438 next month. A box sized to the digits you happened to draw clips the moment the count grows. Use min-width at single-digit size plus horizontal padding, so the shape stays a circle at one digit and grows into a pill at three, with font-variant-numeric: tabular-nums so the width changes only when the digit count does.
If a growing number leads a label, reserve its column. A pill that widens in a flex row pushes its label sideways, so a list stops sharing a left edge and reads as ragged. Put the number in a fixed-width cell — 40px for a 22px pill, 44px for a 26px one — left-aligned inside. The pill still grows; the label does not move. Anything else leading the same list — an icon, a status dot — goes in the same cell, so every row starts at one x.
A list of rows is a grid, not a stack of flex rows. Give the list one grid-template-columns and let every row — and its header — read the same one. A flex row with a flex: 1 spacer places only some of its cells, so each row negotiates its own widths and a wider count or a longer label in one row shifts that row alone. Under a shared grid the columns hold whatever any single row contains: 44px minmax(0, 1fr) auto for a leading mark, a label and an action.
Cap at four digits. Past 9999, show 9999+. A five-digit count is not something a user acts on, and it is wide enough to cost the label its space.
A row's align-items: center centres its cells, not the content inside them. An inline-block in a grid cell — a chip, a status pill, a badge — sits on the text baseline, about 2px low against the text cells beside it. The cell itself has to be display: flex; align-items: center. This is the most common alignment fault in a data table, because it looks correct until a chip sits next to a plain text cell.
An overlay on an image needs its own edge. Anything placed over a photo — a checkbox, a badge, a tag — carries 0 1px 4px rgba(27, 26, 23, 0.28), because the lightness behind it is not knowable. A white control on a white product shot is invisible; a dark one on a dark photo is too. The shadow costs nothing on a photo that already contrasts and saves the one that does not.

ALWAYS FULL WIDTH OF ITS CONTAINER
Tables and item lists. A table narrower than its column leaves the row-hover band ending in mid-air.
Drop zones. The target should be as large as the space allows.
Progress bars and their pace markers. The bar is a proportion, so its full width has to mean the limit.
The sticky save bar and the bulk-action bar. Full width of the main column, not the page — they belong to the content, not the shell.
Cards. A card always fills its column; its column is what varies.
NEVER FULL WIDTH ON DESKTOP
Buttons. Sized to their label, right-aligned in a group. Full width only inside a mobile sheet, where there is one action and the thumb is the pointer.
Body text. Capped at 640px for prose, 900px for a description line. A 1200px line of 13px text can't be read back to its own start.
A form column. Settings caps its cards at 640px even on a 1920px screen — a 42px-tall input stretched to 1200px looks like an error.
Segmented controls, chips, steppers, swatch rows. Intrinsic width, align-self: flex-start. Stretching them adds nothing and hides which is selected.
Dialogs and popovers. 440px and 560px respectively, centred — never a proportion of the viewport.
ROWS
A list row is one line by default. Height comes from padding — 12–14px vertical, 8px in compact — never from a fixed height, so a row with a 26px icon tile grows correctly instead of clipping it.
Columns in a row are fixed except one. In 2b: checkbox 34px, order 2.1fr, date 104px, categories 1.3fr, items 78px, status 118px, amount 150px right-aligned, actions 40px — and the fluid cells absorb the slack. This is what keeps every value at the same x position down the list.
Second lines never displace the first. An item preview or a meta line sits below the primary, inside its cell. Nothing is allowed to move the vendor name.
Rows in a table share one grid definition with the header — declared once on a shared class or a CSS variable, not repeated per row, or the header drifts out of alignment the first time a column changes.
An expanding row pushes, never overlays. Item editing (1b) grows the row and moves the rest down; nothing floats above its neighbours.

THE TEST, IN ORDER
1
Is it one calculation or one object? Keep it grouped. Quantity × price, photo + its controls, icon + its name.
2
Would each part fall under 100px? Stack it, whatever the answer to 1 was. Three fields at 375px minus padding is 105px each before gaps — that is the hard floor, and it is why nothing keeps thirds on a phone.
3
Does one part have an intrinsic width? Fixed plus fluid, not halves. A stepper and a name field, an amount and its currency.
4
Otherwise, full width. The default, and the right answer for most fields.
Implementation: a single container query or breakpoint that flips the field grid from 1fr 1fr to 1fr, with the groups that survive marked explicitly rather than each screen re-deciding. The exceptions are few enough to name — the item equation, the photo row, and the icon-plus-name field.
ALSO CHANGES BELOW 640px
Buttons in a sheet go full width, stacked, primary on top — the only place a full-width button is correct. In a page they stay right-aligned.
Dialogs become sheets, anchored to the bottom, radius on the top corners only.
Comboboxes become full-screen sheets with the search field at the top, above the keyboard — not a 200px popover under a field the keyboard is covering.
Segmented controls may go full width — the one exception to their intrinsic-width rule, because two thumb targets side by side want the room.
The sticky save bar spans the viewport and respects the safe-area inset, sitting above the keyboard rather than under it.
Labels stay above their fields. No inline or left-aligned labels at any width — the vertical rhythm is the same on both, only the column count changes.

THE TEST
Does the number describe a thing, or the space around it? A rail is 360px because a form needs 360px — that travels. A card is 430px in these files because two of them plus a gap fit the page I was drawing on — that does not.
Put differently: every fixed width in the app is on something that holds controls — a rail, a nav, a dialog, a table column. Everything that holds content is fluid, with a minimum and sometimes a maximum.
HOW TO WRITE IT INSTEAD
min-width, not width. The main column is 1fr with min-width: 560px — it never has a width of its own.
auto-fill, not a column count. Order cards are repeat(auto-fill, minmax(280px, 1fr)). Nothing anywhere says "three across".
max-width for reading, not width. A 640px cap on a form column is a ceiling, not a size — at 500px available it is 500px wide.
Container queries over viewport breakpoints for anything inside a column. A field grid should stack because its column got narrow, not because the window did — that is what makes the same form work in a 360px rail and a 640px page.
Height from content and padding. No fixed heights outside the deliberate ones in 14a (the 42px control) — a row with a 26px icon tile must grow, not clip.
CHECK IT AT THESE WIDTHS
1920, 1440, 1280, 1024, 900, 768, 430, 375, 320. Not because they are devices, but because each one crosses something: a breakpoint, a rail's disappearance, or a minimum. A layout correct at all nine is correct everywhere between them.
The two that catch the most: 1024, where the facet rail has gone but the two-column layout has not, and 320, where the mobile field floor actually bites.
And check 1920 with the sidebar collapsed — the widest the main column ever gets, and where a missing max-width shows up as a 1700px line of 13px text.
15d Table columns — widths, and the last two
Every data list in the app is one grid definition shared by its header and its rows. The interesting part is not the widths themselves — it is which column absorbs a resize, and how the amount and the action menu behave when everything else moves.
THE ANATOMY
Exactly one column is fluid. Everything else is a fixed px width. The fluid one is the name — vendor, category, order. Every resize is absorbed there, so no other column ever changes width and none of them need to be re-measured at a new viewport.
The fluid column is minmax(0, 1fr), never 1fr. A bare 1fr has an automatic minimum of its content, so it refuses to shrink below the longest name and the row overflows instead of truncating. This one missing minmax is the single most common cause of a table blowing out of its container.
Fixed columns are sized to the longest value the FORMAT can produce, not the longest in the sample data. A date column is wide enough for 31/12/2026; an amount column for the largest number the currency will realistically print, plus its suffix. Data grows; formats do not.
One definition, declared once. Put the template in a custom property on the table and let the header and every row read it. Two copies means the header drifts from its rows the first time a column changes — and it will be off by exactly one column, which is the hardest kind to see.
THE LAST TWO COLUMNS
The action column is 40px, fixed, and never leaves. It fits one 32px icon button centred in it. It is not part of the responsive story at all: a row without its menu has no way to reach Duplicate or Delete, at any width.
The amount is the second-to-last column, right-aligned, and also never leaves. Right-aligned so the decimal points stack — that is the whole reason a money column is readable at a glance — with font-variant-numeric: tabular-nums and white-space: nowrap. It never wraps and never truncates; if it does not fit, a different column had to go.
Do not put the action column against the container edge. The row's own 14px padding is what separates the kebab from the border. The gap between the amount and the kebab is the grid's ordinary 12px — no extra margin, no margin-left: auto on either. The moment one of them is pushed by a margin instead of placed by the grid, the two stop agreeing at some width.
Never justify-content: space-between on a row. It looks identical at one width and diverges at every other, because the free space lands between the last two items instead of inside the fluid column. If a row is a grid, every cell is placed; if it is a flex row with a spacer, only some are.
The menu opens right-aligned to its own column, and flips above the trigger near the bottom of the list — 14g owns that behaviour. It is anchored to the 40px cell, not to the row, so its position does not move when a column is dropped.

WHAT MOVED, AND WHAT DID NOT
Only the fluid column changed width. Checkbox 18, date 104, category 118, items 130, total 130, actions 40 — identical in all three. Compare any fixed cell across the frames and it lines up.
Columns are dropped whole, in a fixed order, and the header drops the same one in the same step. Items first, then category, then date. What goes last is what nothing else on the screen can tell you.
A dropped column reappears as a second line, not as nothing. At the narrowest width the date, category and count fold under the name as one muted line. The row keeps its meaning; it just stops being a table.
Amount and menu hold their positions relative to the right edge at every width. That is the pair the eye returns to, so it is the pair that must not move.
Hide with the query, not with an inline style. An inline display: flex on a cell beats the stylesheet, so the query’s display: none never lands and the row wraps to a second line. Centring belongs in the class; display belongs to the query.
Verify by counting, not by looking. Header child count must equal every row’s child count at every width, and no grid may report a 0px first column. Both failures look almost right and read completely wrong.
15e The list toolbar
One card above every data list. It has been drawn three times in this set and came out slightly different each time — this is the version all of them now use, so there is nothing left to invent.
THE PARTS, AND THEIR ORDER
Always the same order, left to right: search (fluid) · spacer · optional segmented control · optional Filters · sort. Search is the only fluid item; everything else is flex: none. Nothing is ever centred, and the sort control is always last.
The card is 14px 16px, radius 12, on #fff with the hairline border — the same card every other surface uses. It sits 14px above the list, from the column’s gap, never a margin.
Every control inside is 42px tall with radius 10. Not 9 — the controls sit inside a radius-12 card, and 10 is what reads as concentric. This is the one place the input radius differs from 14a’s 9px, and it applies to all of them so nothing looks odd next to anything else.
Set the height explicitly on every one of them: box-sizing: border-box; height: 42px. Do not size any of them by padding. A search field is a text box and gets 42px from 10px 12px padding; a segmented control is a 3px-padded track holding two centred cells; a sort control is an icon and two labels in a row. Left to their own padding those come out 42, 36 and 38 — the row then aligns on nothing, and the difference is small enough to look like an accident rather than a bug. This has already happened twice in this set.
Segment cells fill their track with flex: 1 and display: grid; place-items: center — no vertical padding of their own. Padding inside a fixed-height track leaves the label sitting above centre while the track itself measures correctly, which is the harder version of the same fault to spot.
Check it by measuring, not by looking. Every direct child of the toolbar must report the same height. One value, no exceptions — a 40px control beside a 42px one is invisible in a screenshot and obvious in a row.
Search always carries the ⌘K badge, and gains a round clear button to its left once there is a query. The query renders in #1b1a17, the placeholder in #8b8a82 — a placeholder that stays visible beside a typed value is not a thing an input does.
Sort shows its label and its value, not a bare value. “Sort” in 12px #6b6a63, the value in 13px/600 — a control reading only “Newest first” is a mystery until opened.
The result count is not in the toolbar. It belongs on the list’s own header strip, where it sits beside the thing it counts. Putting it here means it competes with the controls for the same row.

WHAT IS OPTIONAL, AND WHEN
Search and sort are never optional. Every list has both, even a nine-row category list — the sort a list opens with is a setting, so the control that changes it has to exist.
A segmented control appears only for a state that partitions the list and is not a filter: Active/Archived on vendors, rows/cards on orders. Two or three options, never four. If it would take four, it is a sort or a filter.
Filters appears when the list has a facet rail that can be hidden, and carries the count of applied facets as a badge. Zero applied means no badge, not a “0”. Below 1280px the rail becomes a drawer and this button is how it opens; above that it still exists, because a collapsed rail must be reachable at any width.
Nothing else goes in here. No New button — creating lives in the sidebar. No export, no view menu, no bulk actions: the bulk bar replaces the toolbar in place when a row is ticked, which only works because the two are the same height.

WHAT MOVED, AND IN WHAT ORDER
This is a container query on the list column, not a viewport media query. Collapsing the sidebar widens the column without the viewport changing, and the toolbar has to respond to that — the same rule as the tables in 15d. The one exception is the two-row break, which coincides with the phone layout.
Things leave in order of how little they cost: the ⌘K hint (the shortcut still works) · the sort value, leaving its label and chevron · then the row splits. Nothing is ever narrowed to the point of truncating its own label.
Search keeps its placeholder meaningful as it shrinks. The long placeholder is replaced by a shorter one rather than being ellipsised — “Search vendor, item, refe…” tells the user less than “Search orders…” does.
Two rows, never a wrap. Search takes the first row alone; every remaining control shares the second with flex: 1. Letting the row wrap naturally leaves one control stranded on a line of its own at some widths, which looks like a bug because it is one.
This is the only place a toolbar control stretches. Everywhere else they are flex: none at their intrinsic width — see the never-full-width list in 15a. On the second row they are thumb targets, so the room is worth having.
Below 640px Filters opens a bottom sheet, not a drawer, matching the phone filter pattern. The button itself does not change; only what it opens does.
Every control stays 42px at every width. Nothing shrinks vertically — on touch that is already at the 44px floor, so taking height out is the one change that would break usability rather than just looks.
