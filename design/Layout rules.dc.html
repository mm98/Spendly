15a Columns, rows, and what goes full width
Every screen in the set uses one of four column shapes, and every field is either full width or a fraction for a reason that can be stated. Written down here because it was consistent across the designs but never explicit — and an undocumented grid is the first thing to drift.
THE ONE RULE BEHIND ALL OF IT
One fluid column per layout. Everything else is a fixed pixel width. The main column takes 1fr; rails, navs and facet columns are fixed. Two fluid columns means neither has a predictable width, so nothing inside either can be sized with confidence — and the first long vendor name changes the whole page.
Gaps, not margins. 24px between columns, 14px between stacked cards, 16px in a card grid, 12px between fields. Set on the container, never per child, so reordering and deleting stay safe.
An overlay's inset is never a free number. A control positioned over something — a checkbox on a card, a badge on a thumbnail, a PDF tag on an attachment tile — is inset by the padding of whatever it must line up with, not by whatever looks about right. A card's checkbox sits 16px in because the bulk bar above it has 16px padding, so the two checkboxes share an x. Pick the element it aligns against first, read its padding, use that number.
A row's align-items: center centres its cells, not the content inside them. An inline-block in a grid cell — a chip, a status pill, a badge — sits on the text baseline, about 2px low against the text cells beside it. The cell itself has to be display: flex; align-items: center. This is the most common alignment fault in a data table, because it looks correct until a chip sits next to a plain text cell.
An overlay on an image needs its own edge. Anything placed over a photo — a checkbox, a badge, a tag — carries 0 1px 4px rgba(27, 26, 23, 0.28), because the lightness behind it is not knowable. A white control on a white product shot is invisible; a dark one on a dark photo is too. The shadow costs nothing on a photo that already contrasts and saves the one that does not.

Statistics uses a 12-column grid where every card spans a whole number of columns, so rows always close — no half-filled row, no gap in the middle. Verify at 1280, 1440 and 1920.
Cards in a grid row share a height, cards in a column do not. Grid handles the first automatically; don't fight it with fixed heights.
FIELDS — FULL WIDTH, OR A FRACTION
The test is the content, not the importance. A field goes full width when what it holds has no predictable length. It takes a fraction when its content is a bounded token — a date, a status, a number — where a wide box is just empty space that makes the value look lost.

A control with an intrinsic width — the stepper, an icon tile, a currency suffix — takes flex: none at its own size, and the text field beside it takes the remainder with min-width: 0. The fixed one never stretches to fill; a 400px-wide stepper is absurd.
ALWAYS FULL WIDTH OF ITS CONTAINER
Tables and item lists. A table narrower than its column leaves the row-hover band ending in mid-air.
Drop zones. The target should be as large as the space allows.
Progress bars and their pace markers. The bar is a proportion, so its full width has to mean the limit.
The sticky save bar and the bulk-action bar. Full width of the main column, not the page — they belong to the content, not the shell.
Cards. A card always fills its column; its column is what varies.
NEVER FULL WIDTH ON DESKTOP
Buttons. Sized to their label, right-aligned in a group. Full width only inside a mobile sheet, where there is one action and the thumb is the pointer.
Body text. Capped at 640px for prose, 900px for a description line. A 1200px line of 13px text can't be read back to its own start.
A form column. Settings caps its cards at 640px even on a 1920px screen — a 42px-tall input stretched to 1200px looks like an error.
Segmented controls, chips, steppers, swatch rows. Intrinsic width, align-self: flex-start. Stretching them adds nothing and hides which is selected.
Dialogs and popovers. 440px and 560px respectively, centred — never a proportion of the viewport.
ROWS
A list row is one line by default. Height comes from padding — 12–14px vertical, 8px in compact — never from a fixed height, so a row with a 26px icon tile grows correctly instead of clipping it.
Columns in a row are fixed except one. In 2b: checkbox 34px, order 2.1fr, date 104px, categories 1.3fr, items 78px, status 118px, amount 150px right-aligned, actions 40px — and the fluid cells absorb the slack. This is what keeps every value at the same x position down the list.
Second lines never displace the first. An item preview or a meta line sits below the primary, inside its cell. Nothing is allowed to move the vendor name.
Rows in a table share one grid definition with the header — declared once on a shared class or a CSS variable, not repeated per row, or the header drifts out of alignment the first time a column changes.
An expanding row pushes, never overlays. Item editing (1b) grows the row and moves the rest down; nothing floats above its neighbours.

THE TWO THINGS THAT GO WRONG
Shrinking instead of removing. Every breakpoint here removes or relocates something. Nothing is scaled down: a compressed facet rail, a four-column equation at 300px, or a table squeezed into a phone row are all the same mistake.
A second fluid column. The moment two columns are both 1fr, nothing inside either can be sized, truncation stops being predictable, and the first long vendor name reflows the page. One fluid column, always.

THE TEST, IN ORDER
1
Is it one calculation or one object? Keep it grouped. Quantity × price, photo + its controls, icon + its name.
2
Would each part fall under 100px? Stack it, whatever the answer to 1 was. Three fields at 375px minus padding is 105px each before gaps — that is the hard floor, and it is why nothing keeps thirds on a phone.
3
Does one part have an intrinsic width? Fixed plus fluid, not halves. A stepper and a name field, an amount and its currency.
4
Otherwise, full width. The default, and the right answer for most fields.
Implementation: a single container query or breakpoint that flips the field grid from 1fr 1fr to 1fr, with the groups that survive marked explicitly rather than each screen re-deciding. The exceptions are few enough to name — the item equation, the photo row, and the icon-plus-name field.
ALSO CHANGES BELOW 640px
Buttons in a sheet go full width, stacked, primary on top — the only place a full-width button is correct. In a page they stay right-aligned.
Dialogs become sheets, anchored to the bottom, radius on the top corners only.
Comboboxes become full-screen sheets with the search field at the top, above the keyboard — not a 200px popover under a field the keyboard is covering.
Segmented controls may go full width — the one exception to their intrinsic-width rule, because two thumb targets side by side want the room.
The sticky save bar spans the viewport and respects the safe-area inset, sitting above the keyboard rather than under it.
Labels stay above their fields. No inline or left-aligned labels at any width — the vertical rhythm is the same on both, only the column count changes.
15c Which numbers are real
A mockup has to be some width to be drawn, so these files are full of pixel values that are scaffolding rather than specification. Read the wrong ones as spec and you get an app that is pixel-perfect at 1400px and broken at every other size. This says which is which.

THE TEST
Does the number describe a thing, or the space around it? A rail is 360px because a form needs 360px — that travels. A card is 430px in these files because two of them plus a gap fit the page I was drawing on — that does not.
Put differently: every fixed width in the app is on something that holds controls — a rail, a nav, a dialog, a table column. Everything that holds content is fluid, with a minimum and sometimes a maximum.
HOW TO WRITE IT INSTEAD
min-width, not width. The main column is 1fr with min-width: 560px — it never has a width of its own.
auto-fill, not a column count. Order cards are repeat(auto-fill, minmax(280px, 1fr)). Nothing anywhere says "three across".
max-width for reading, not width. A 640px cap on a form column is a ceiling, not a size — at 500px available it is 500px wide.
Container queries over viewport breakpoints for anything inside a column. A field grid should stack because its column got narrow, not because the window did — that is what makes the same form work in a 360px rail and a 640px page.
Height from content and padding. No fixed heights outside the deliberate ones in 14a (the 42px control) — a row with a 26px icon tile must grow, not clip.
CHECK IT AT THESE WIDTHS
1920, 1440, 1280, 1024, 900, 768, 430, 375, 320. Not because they are devices, but because each one crosses something: a breakpoint, a rail's disappearance, or a minimum. A layout correct at all nine is correct everywhere between them.
The two that catch the most: 1024, where the facet rail has gone but the two-column layout has not, and 320, where the mobile field floor actually bites.
And check 1920 with the sidebar collapsed — the widest the main column ever gets, and where a missing max-width shows up as a 1700px line of 13px text.
