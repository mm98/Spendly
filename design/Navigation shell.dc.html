9a Navigation shell
One frame around every area. The sidebar holds the areas and never scrolls away; the top bar is the locked shell. It carries search and nothing else — no page title, and no actions of any kind, global or page-level. Everything the app can do lives inside a page or in the sidebar, which is why the edit screen has a sticky save bar, the list puts bulk actions above itself, and Scan receipt sits at the top of the sidebar where it is reachable from every screen.
NOTE ON THE FRAME
The content column is deliberately empty — this frame has no content of its own, and every screen in the set renders in that column. Other files redraw this bar around their own screen so each reads in context — 9a is the one that governs it. A page heading sits in the content column at 20px/600, on the same x as the content below it, and carries no back control: the sidebar is always visible and is the way back, browser back already works, and a screen reached from a sidebar action has no previous page for an arrow to point at. Leaving a record is Cancel or Discard in the page, or picking another destination. There is no page heading anywhere — not in the bar and not at the top of the content column. The sidebar names the area, and a record identifies itself in its own content: the order list by its rows, an order by its vendor and reference in the details rail. A heading above either would repeat what is already on screen. If they ever disagree, this file is right, and the difference is a bug in the other file rather than a variant.
The rounded corners, the 1px outline and the drop shadow around the shell below are presentation only — they exist so the mockup reads as a window on this page. In the app the shell fills the browser viewport edge to edge: the sidebar runs the full height with square corners, and the content column meets the window edge with no border and no radius. Same for the fixed 1400px width, which stands in for a viewport.

WHAT IS NOT IN IT
Anything destructive. No delete, no merge, no undo. A palette is typed fast and confirmed by reflex; it is the wrong surface for something irreversible.
Anything that acts on the current page. No "save this order", no "add a line". Page actions live on the page, and a command whose meaning depends on what is behind the overlay is unpredictable.

BEHAVIOUR
560px, centred, top-anchored at 15vh. Radius 14px, shadow 0 14px 32px rgba(27,26,23,0.14), scrim rgba(27,26,23,0.35). It does not grow past 60vh; the result list scrolls inside it.

Actions rank above records only when the query matches a command name. Typing a vendor name should never put "Switch to dark mode" first.
Search is debounced 300ms and cancels in flight. The previous results stay visible while the next load runs — the list never blanks between keystrokes.

Unsaved changes prompt before it navigates, the same as any other navigation.
Not on mobile. Below 640px ⌘K has no meaning and the search field goes to the order list instead.

The rail is read-only until Edit is pressed. Save current takes Edit's slot whenever the current filters differ from the active view — saving concerns the state you are in now and outranks reorganising. Drawn in 2g. Nine views out of ten a user opens this card to switch view, not to reorganise it; drag handles on every row put a maintenance affordance in front of the navigation task and make the list read like a settings screen. At rest it is names, icons and counts. Edit reveals handles and a per-row menu with Rename and Delete; Done leaves. All orders shows as locked in that mode rather than disappearing, so the list does not reflow when the mode changes.
Edit is a button, not a hover. It is visible at rest on every device — the objection to hover-revealed affordances (16f) is about things that need a cursor to be discovered, not about modes entered deliberately.
Save current replaces Edit in that slot when the filters differ from the active view, because saving is about the state you are in now and outranks reorganising. Reordering saves on drop; there is no separate save.
One list, one order, two renderers. Both read the same saved-views collection and the same counts. Do not give the sidebar its own hardcoded items — "Awaiting delivery" and "Missing receipt" are saved views that ship as defaults for a new account, not navigation the code knows about.
A newly saved view inserts at position 2 — directly under All orders, at the top of the saved list — so the save is visible immediately in both surfaces. Appending to the end would drop it into the overflow on any account that already has four views, and saving would appear to do nothing. It stays where it lands until the user drags it in the rail; nothing re-sorts on its own.
The sidebar shows the first four, then a count. A fixed height matters more here than completeness: the sidebar has a pinned bottom zone (9a) and a rail that must not grow without limit. Which four is controlled by dragging in the rail — there is no separate pin or "show in sidebar" flag, because a second mechanism for the same intent is a second thing to keep in sync.
All orders is always first and always shown, in both. It is not a saved view: it cannot be renamed, reordered or deleted, and it has no menu. Making a saved view the default changes what Orders opens to; All orders keeps its position.
Selecting from the sidebar navigates to the order list with that view's URL applied, exactly as selecting it in the rail would. Arriving that way, the rail shows the same row selected — there is no state where the two disagree about which view is active.
The counts are live and identical. One request returns the counts for every view; both surfaces render from it. A count the sidebar has not received yet renders as nothing, not a zero (2g).
A view can carry an attention flag, and both surfaces honour it — "Missing receipt" here. The flag is a property of the view, set when it is saved, never derived from the number, and a count is never red. Like status colour (11a), the flag names a pair, one ink per surface: #d3b98a on the dark sidebar, #7a5c23 at weight 600 on the rail's white card. Both are authored — the dark tint on white fails contrast, so neither is computed from the other.
Collapsed (9b) and mobile. Collapsed, the group shows only All orders' icon; individual views are not distinguishable as 17px glyphs. On the phone tab bar, Orders is one destination and views are reached from the rail's sheet.
9f The shell contract
What the shell may hold, what it may not, and how each part behaves when the text is too long or the screen too narrow. The shell is shared by every page, so a page that adds something here changes every other page — which is why the permitted list is short and closed.
THE TOP BAR
Search — one field, 420px fixed, left-aligned and flush with the content column's padding, opening the ⌘K palette. Permitted because it navigates: nothing it does changes a record.
A page title — of any kind. The sidebar's active row already names the area, and a record's name is the page's own heading inside the content column. A title in the bar duplicates one and misstates the other.
Any action — page-level or global. No Save, no New order, no Scan receipt, no export, no overflow menu. There is no global-action exception.
Anything page-specific — filters, counts, tabs, a status. The bar is identical on every screen in the app.
The account block — it lives at the bottom of the sidebar (9c), not top-right. Do not add a second one.
Where an action goes instead: a sticky bar at the bottom of the content column (save), a bar above the list (bulk), a button inside the page (edit, delete, export), or the sidebar — which holds exactly two, Scan receipt and New order, because they create the thing the whole app is about and must be reachable from every screen. Wanting a third sidebar action is the rule working, not a gap.

The shell takes no children from a page. No slot, no portal, no useTopBarActions hook. If the shell cannot be extended, the constraint holds by construction rather than by review — and every one of these rules stops needing to be checked.
The page title comes from the route, not from the page's own render. A page that sets its own title can set anything, which is how a record name and then a status chip end up in a locked bar.
Every truncating text needs min-width: 0 on its flex parent. Without it the item refuses to shrink below its content and pushes its siblings out instead of clipping — the single most common cause of a shell that overflows at 1280px but looks fine at 1440px.

One icon column, brand included. WHAT NOT TO DO
Don't shrink rows. 40px is already the floor and the touch target depends on it. Height comes off the list, never off a row.
Don't trim the saved views. Showing three instead of four makes the "N more" count change with the window, which reads as data appearing and disappearing.
Don't scroll the whole sidebar. The brand scrolling away is disorienting, and the account block is the one thing that must always be reachable.
NOTES FOR IMPLEMENTATION
This is a container query on the sidebar's own height, not a viewport media query. The sidebar is 100dvh — dvh, not vh, because mobile browser chrome makes vh wrong by exactly the amount that causes this problem.
The scrolling region is the nav only: flex: 1; min-height: 0; overflow-y: auto. Without min-height: 0 a flex child refuses to shrink below its content and pushes the bottom zone off-screen instead of scrolling — the same automatic-minimum-size rule as 13a, and the single most likely thing to go wrong here.
The fade is a mask, not a gradient overlay. mask-image: linear-gradient(to bottom, #1b1a17 calc(100% - 22px), transparent) on the scroll container. An overlay would need to match the sidebar colour and would break the moment the theme changes; a mask does not care.
The fade only shows when there is more below. A permanent fade at the bottom of a fully-visible list reads as a rendering fault. Toggle it from the scroll position.
The brand is outside the scroll region — a wordmark that scrolls away leaves the sidebar looking like a detached list, and it is the only fixed point at the top. Same for the bottom zone at the other end. Scrollbar: 6px, thumb rgba(255,255,255,0.14), transparent track, visible on hover and while scrolling. Never the platform default — a light scrollbar on #14261c is the brightest thing in the sidebar.
Scroll the active row into view on load, nearest-edge, no animation. Landing on Categories with the nav scrolled to the top hides where you are.
The collapsed rail (9b) has the same three tiers and the same rules — it is shorter per row, so it reaches each threshold later, but nothing about the behaviour differs.
9h The shell below 1280px and below 640px
Two breakpoints change the shell itself, and they are the only two that do. At 1280px the sidebar collapses to the icon rail; at 640px it leaves the side of the screen entirely and becomes a tab bar. Frames are drawn at 768px and 390px, but the rule is the threshold, not the device.
NOTES FOR IMPLEMENTATION
Below 1280px is the collapsed rail, not a new layout. Same three zones, same order, labels become tooltips. Saved views drop out — they are the one group that cannot be told apart as 19px glyphs. Everything else survives one-to-one.
Below 640px the sidebar is a bottom tab bar, not a drawer. Four destinations — Home, Orders, Statistics, More — with Settings, the theme toggle, the account and saved views inside More. A hamburger drawer puts the most-used navigation two taps away on the device where capture matters most.
Scan receipt becomes the floating action button and is the only FAB in the app. It leaves the nav because the phone is the camera: it is the one action that must be reachable from every screen without a tab change. 56px, bottom right, clear of the tab bar.
The top bar keeps only search at every width. It never gains a title, a hamburger or a back arrow — the tab bar says where you are and the browser says where you came from.
The tab bar and the FAB do not scroll. Content scrolls beneath them, with bottom padding equal to the bar height plus the safe-area inset so the last row is never trapped under it.
These two are viewport breakpoints, and the only ones in the app. Everything else — which table columns are present, how a toolbar wraps — is a container query on the element itself. Collapsing the sidebar widens the content column without the viewport changing at all, and a table must respond to that.
Use 100dvh, not 100vh. On a phone the browser toolbar makes vh wrong by exactly the height of the thing you are trying to sit above.
