NOTES FOR IMPLEMENTATION
One button for the file, not two. Camera versus files is the device's decision, not a design choice: a single input with the right accept and capture attributes gets a camera option on a phone, a photo library on a tablet, and a plain file dialog on desktop — each in the form that platform's users already know. Offering "Choose file" and "Use camera" as separate buttons duplicates the OS picker's own first screen, and one of the two is always dead weight on whatever device you are holding.
Drop is the desktop path and needs no button — the zone is the affordance. Keep the button anyway for keyboard users and for anyone who does not think to drag.
Three ways to start, ranked by frequency: receipt (the common case, so it gets the whole zone), empty order, copy a previous order. Copy is hidden entirely when there are no orders yet.

NOTES FOR IMPLEMENTATION
Every row has to be identifiable without opening it. Vendor alone is not enough — there may be twelve orders from the same shop. The line count, the first item names and the total are what separate them, and the total does most of the work.
Two groups, not a flat list. You order these often is orders whose vendor and line shape have recurred, with the repeat count — that is the case this feature exists for, so it comes first. Recent is the fallback. Same grouped pattern as the vendor Combobox in 14a: arrow keys cross both groups as one list, headers are never focusable.
Search covers vendor and item name, because the thing you remember is often "the order with the oak chairs" rather than the shop. Same 300ms debounce and prefix matching as every other search.
Picking opens the edit screen unsaved. No confirm — nothing exists yet, and the notice's Discard is the way out. This is the same reason the duplicate in 8a needs no dialog.
The copy rules are 8a's, unchanged. Vendor, category, reference, notes and all lines with quantities and prices carry over; date becomes today, status resets, attachments do not follow. The dialog states this up front, because "copy" otherwise implies the receipt comes with it.
Amounts are copied, not re-priced. They are what you paid last time, and they are editable like any other field. Nothing looks up a current price — this is a record of what happened, not a shopping basket.
THREE ENTRY POINTS, ONE DIALOG
Create screen — the third card, hidden when there are no orders yet.
New order split button — the chevron menu, for starting a copy without passing through the create screen.
Home's Duplicate last order — skips the dialog entirely, since "last" needs no picking.
The order list's per-row Duplicate is deliberately not one of these: there the source is already chosen, so it goes straight to the edit screen. This dialog exists only for the case where it is not.
WHY A DIALOG RATHER THAN A LIST PAGE
The order list already does browsing, and has Duplicate on every row — that is the path for "I know which one". This dialog serves the other case: you are starting an order and want the last one like it, without leaving what you are doing.
So it stays small and shows five or six rows with search rather than facets and paging. If you need filters to find the source, the order list is the better tool and Duplicate is waiting there.

NOTES FOR IMPLEMENTATION
Hash on upload, before reading. SHA-256 of the bytes as received, stored on the attachment row and indexed. The check is a single lookup and costs nothing, so it runs on every upload — including the ones that arrive through Import and through the item-photo slot.
It replaces the reading stage rather than covering it. A dialog over a progress bar would mean the scan is running behind a question about whether it should. And asking after the proposal exists wastes the read and puts the user in review with a decision they should have made first.
Store the reading, not just the hash. The scan output is cached against the file hash, so a repeat upload can produce a full order without a second API call. This is the whole return on the feature: the three legitimate reasons to continue — a repeated purchase on an identical receipt, a re-import after deleting the original, and one receipt covering two orders — are all served for free by the cached reading. None of them needs the scanner to look at the same bytes twice.
The cost is ours, so it stays out of the UI. Each scan is a paid API call, which is the reason this screen exists — but a per-action price tag would make the user manage our infrastructure bill, and they cannot act on a figure they did not agree to. The design carries the intent instead: reusing the reading is the primary button and reads as the obvious choice, re-reading is a secondary. No amounts, no warnings, no counters.
Never blocks. Re-reading is legitimate when the cached reading was wrong and the model has improved since — the one case where a second call is worth making. It stays one click.
Show the matched order, not just the fact. Vendor, reference, date, line count, total, and when it was scanned. "You have already imported this file" without the order is a dead end — the user's next question is always which one, and answering it here saves a trip to the list.
Compare the files opens both in the viewer (12b) side by side. Rarely needed for an exact hash match, but it is the only way to be sure the stored file is what you think it is — and it costs one link.
Attach instead is shown disabled here on purpose: the matched order already holds this exact file, so there is nothing to add. It is enabled when the hash matches a file sitting on a different order — you scanned this receipt for order A and now want it on order B. When disabled, the tooltip says why ("SPENDLY-447 already has this file"); the row is not hidden, because its absence would leave the user wondering whether attaching is possible at all.
Multiple matches list up to three orders, newest first, with a count if there are more. Each row carries its own "Open that order".
WHAT THE HASH DOES AND DOES NOT CATCH
Catches: the same file uploaded twice — the common case, where a receipt was already forwarded once and lands in the uploads folder again, or a phone photo is re-picked from the library.
Misses: a second photo of the same paper receipt, the same PDF re-saved by a different reader, or a re-download that changed one byte of metadata. All are different bytes and therefore a different hash.
So this is not duplicate-order detection, and must not be presented as such. The fuzzy check on vendor plus date plus total — the one behind "2 rows look like orders you already have" in Import (11b) and the possible-duplicates list in 5c — is the separate mechanism that catches those, and it runs later, on the proposed order rather than on the file.
Both can fire on one upload. When they do, this screen comes first — it is certain, and it is the only one of the two that can run before the scanner is called at all.
