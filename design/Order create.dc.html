3a New order - scan a receipt
Three steps: pick a way to start, drop the file, then check what was read - in the ordinary edit screen, which is also where you stay once it is saved. Reviewing a scan and editing a saved order are one screen in two states, not two screens. Nothing becomes an order until you create it: from the moment the file is uploaded the scan is kept as a draft, and every extracted value stays editable.

Notes for implementation
Jump to first moves focus to the first value that needs a look and scrolls it into view. It shows on a phone too: the values that need a look are there as well.
One button for the file, not two. Camera versus files is the device's decision, not a design choice: a single input with the right accept attribute, and no capture, gets a camera option beside the library on a phone, a photo library on a tablet, and a plain file dialog on desktop - each in the form that platform's users already know. Offering "Choose file" and "Use camera" as separate buttons duplicates the OS picker's own first screen, and one of the two is always dead weight on whatever device you are holding.
Drop is the desktop path and needs no button - the zone is the affordance. Keep the button anyway for keyboard users and for anyone who does not think to drag.
Three ways to start, ranked by frequency: receipt (the common case, so it gets the whole zone), empty order, copy an order. Copy is hidden entirely when there are no orders yet.
A button that says Empty order opens an empty order directly - the edit screen, not created yet - wherever it appears (Home, Statistics, the order list's empty state). Only New order shows step 1, because only New order leaves the choice open.
Categories come from the vendor's defaults (5l), the one source: filled when the field is empty, with "filled from" and the vendor's name beside the label. Categories the items point to and the vendor's defaults lack are offered under the field, to pick (step 3).
Two ways in. New order (the sidebar row, the + on the rail, the phone's FAB) opens step 1, these three choices. Scan receipt (the sidebar's green row and the rail's capture tile) skips step 1: it opens the file picker at once, and the chosen file arrives at step 2 as if it had been dropped here. Cancelling the picker leaves the user on the page they were on.

One screen, two states
The two renders above are the same screen. Same grid, same cards, same order of fields - what differs is whether the order exists yet, and that is four things.
A tick on every line, and the confidence tones, belong to the unsaved state: a line can still be left out, and a value read badly is marked amber. Once the order is saved there is nothing to leave out, so the column and the tones go.
The bar at the top changes tone, not place: amber with a count of values to look at while the order is a proposal, green with the file it came from once it is created.
The action pair is Discard / Create order, then Cancel / Save. Same footer, same two slots.
Attachments is the same card in both states, beneath the lines, with the scanned file as its first attachment. Opening it is the viewer (12b), as on any order. The file is never shown beside the form.
Building it twice would produce two screens in code that have to be kept identical by hand. It is one screen with an unsaved flag.
A scan is a draft until it is created or discarded
The scan is an order with status Draft from the moment its file is uploaded, through the reading and the review, until Create or Discard. Leaving in any other way keeps it: Back, another page, closing the tab or the app, a phone put away while it reads. There is no Save as draft button and no question on leaving. Leaving the review shows the toast "Kept in Drafts", with no Undo, since nothing was lost. Like every draft it moves no money until it is created.
What is on the screen is what is kept. The review is written to the draft as it is edited: the values as changed, the lines ticked and unticked, and the marks - which values were hard to read, which lines were unsure, which of them have been touched. A draft never removes itself, and its file stays with it for as long as it exists.
Opening a draft later is step 3 exactly as drawn, on desktop and on a phone: the amber bar with the count still to look at, the ticks, the tones, Jump to first. A value touched before leaving stays cleared. The file is in Attachments, beneath the lines. A draft whose reading has not finished opens step 2, and step 3 when the reading is done. It opens from Home's Drafts card, the order list (status Draft) and the palette's Drafts.
Create turns the draft into an order with the status a scan gets today: the account's default status, or the one the document shows when Settings, Defaults lets a scan set it (11a). The button stays Create, the rule on every new record: the draft is not an order until then. Discard is the 6d dialog (6d), because the file goes with it.
Without a reader key the blank scan is kept as a draft the same way: the file, and no values.
An order made by hand is a draft from its first change
An empty order and a copy become a draft at their first change: a character typed in any field, a vendor or category picked, a line added or removed, a file attached. What the form opens with - today's date, the default status, a copy's carried-over lines - is not a change. Until then nothing is kept, leaving says nothing, and Drafts does not fill with forms nobody typed in. A copy left untouched has lost nothing: its source is still there.
Leaving it keeps it, as a scan is kept. Back, another page, closing the tab or the app: no question, and the toast "Kept in Drafts" with no Undo. There is no "Leave without saving?" on a new order. Editing an order that is already created keeps the unsaved-changes prompt, since that order already exists as it was.
Reopening it is the edit screen as it was left, footer Discard / Create, and a copy keeps its green notice naming the order it came from. Create gives it the account's default status, as any new order.
Discard without files is a toast, "Draft discarded" with Undo, since nothing beyond the form goes (6d, 6f). A draft holding a file or a photo uses the 6d dialog, naming them. Before the first change Discard just closes the form.
Category suggestions
Vendor defaults fill the field; suggestions sit under it. A suggestion is a dashed chip and adds nothing until it is tapped. Tapped, it moves into the field as an ordinary chip - the saved state above shows Lighting taken and Seating left.
A category that does not exist yet says so in its label: "+ New: Seating". Tapping it creates the category and adds it to the order in one step. Existing categories read "+ Lighting".
Two sources. Item names matched against earlier orders run by themselves, on every order edit screen, recalculated when lines change - they are free and instant. The model, given the item names, the vendor and the user's category list, runs only on the bulb button, and is the only source that proposes a new category.
A scanned order has no button while it has suggestions: the scan's own model call returns them. The button shows only when that call found none.
The button is the bulb icon at the end of the token field, labelled "Suggest categories" for screen readers and as its tooltip. It stays in place in every state. Pressed, its icon becomes the spinner until the answer arrives; pressed again, it asks again.
Only confident suggestions are shown, at most three; none is better than a wrong one. No row when there is nothing to suggest, except after a press, which answers "No suggestions for these items". No suggestion repeats a category in the field, and one removed from the field is not offered again on this order.

Notes for implementation
Every row has to be identifiable without opening it. Vendor alone is not enough - there may be twelve orders from the same shop. The line count, the first item names and the total are what separate them, and the total does most of the work.
Two groups, not a flat list. You order these often is orders whose vendor and line shape have recurred, with the repeat count - that is the case this feature exists for, so it comes first. Recent is the fallback. Same grouped pattern as the vendor Combobox in 14a: arrow keys cross both groups as one list, headers are never focusable.
Search covers vendor and item name, because the thing you remember is often "the order with the oak chairs" rather than the shop. Same 300ms debounce and prefix matching as every other search.
Picking opens the edit screen, not created yet. No confirm - nothing exists yet, and the notice's Discard is the way out. The copy becomes a draft at its first change, as an empty order does (3a). This is the same reason the duplicate in 8a needs no dialog.
The copy rules are 8a's, unchanged. Vendor, category, reference, notes and all lines carry over whole - quantities, prices and each line's photo; date becomes today, status resets, the order's files are not copied. The dialog states this up front, because "copy" otherwise implies the receipt comes with it.
Amounts are copied, not re-priced. They are what you paid last time, and they are editable like any other field. Nothing looks up a current price - this is a record of what happened, not a shopping basket.
Two entry points, one dialog
Create screen - the third card, hidden when there are no orders yet.
Home's Copy an order - the button in the Add an order card, beside Empty order. Opens this dialog over Home; Escape or Cancel leaves you on Home. Hidden when there are no orders yet.
The order list's per-row Duplicate is deliberately not one of these: there the source is already chosen, so it goes straight to the edit screen. This dialog exists only for the case where it is not.
Why a dialog rather than a list page
The order list already does browsing, and has Duplicate on every row - that is the path for "I know which one". This dialog serves the other case: you are starting an order and want the last one like it, without leaving what you are doing.
So it stays small and shows five or six rows with search rather than facets and paging. If you need filters to find the source, the order list is the better tool and Duplicate is waiting there.
3c This receipt has been scanned before
The file's SHA-256 matches one already stored, so this receipt has been read before. It interrupts between upload and reading because the reading is cached - the answer is already in the database, and re-running the scanner on the same bytes buys nothing. The user never sees a cost; they see that reusing the saved reading is simply the faster path.

Notes for implementation
Discard the upload deletes the uploaded file and returns to step 1. Nothing is created.
Hash on upload, before reading. SHA-256 of the bytes as received, stored on the attachment row and indexed. The check is a single lookup and costs nothing, so it runs on every upload - including the ones that arrive through Import and through the item-photo slot.
It replaces the reading stage rather than covering it. A dialog over a progress bar would mean the scan is running behind a question about whether it should. And asking after the proposal exists wastes the read and puts the user in review with a decision they should have made first.
Store the reading, not just the hash. The scan output is cached against the file hash, so a repeat upload can produce a full order without a second API call. This is the whole return on the feature: the three legitimate reasons to continue - a repeated purchase on an identical receipt, a re-import after deleting the original, and one receipt covering two orders - are all served for free by the cached reading. None of them needs the scanner to look at the same bytes twice.
The cost is ours, so it stays out of the UI. Each scan is a paid API call, which is the reason this screen exists - but a per-action price tag would make the user manage our infrastructure bill, and they cannot act on a figure they did not agree to. The design carries the intent instead: reusing the reading is the primary button and reads as the obvious choice, re-reading is a secondary. No amounts, no warnings, no counters.
Never blocks. Re-reading is legitimate when the cached reading was wrong and the model has improved since - the one case where a second call is worth making. It stays one click.
Show the matched order, not just the fact. Vendor, reference, date, line count, total, and when it was scanned. "You have already imported this file" without the order is a dead end - the user's next question is always which one, and answering it here saves a trip to the list.
A file whose draft still exists is "Scanned before" too, pointing to the draft: the record shows its vendor or file name and scan day, and the first button reads "Open that draft", opening it in the review (3a step 3).
Compare the files opens both in the viewer (12b) side by side. Rarely needed for an exact hash match, but it is the only way to be sure the stored file is what you think it is - and it costs one link.
There is no Attach. A matched hash means that order already holds this exact file, so there is nothing to add from here.
Multiple matches list up to three orders, newest first, with a count if there are more. Each row carries its own "Open that order".
One primary on this screen: Open that order. The two alternatives are equal-weight rows with outline buttons, and neither carries the green border. A tinted, bordered option plus its own filled button would be a second primary - and it would recommend the path the user most likely did not want, since a repeated receipt usually means they meant the existing order.
Only the matched order carries a mark. It is a real record, so it shows its photo the way an order row does. The two alternatives are actions, not records - a generic file glyph beside each added nothing the title did not already say, so they are title, description and button only.
The option mark sits on the title's first line (sp-list-item--top), not centred on the block. Centred, it drifts down as the description wraps, and two options with different description lengths stop sharing a mark position.
On a phone every button here is full width and stacked (sp-btn--block), primary first. Small buttons left at their own width stack into a ragged column of two different lengths. See the phone frame in 7a.
What the hash does and does not catch
Catches: the same file uploaded twice - the common case, where a receipt was already forwarded once and lands in the uploads folder again, or a phone photo is re-picked from the library.
Misses: a second photo of the same paper receipt, the same PDF re-saved by a different reader, or a re-download that changed one byte of metadata. All are different bytes and therefore a different hash.
So this is not duplicate-order detection, and must not be presented as such. The fuzzy check on vendor plus date plus total - the one behind "2 rows look like orders you already have" in Import (11b) and the possible-duplicates list in 5c - is the separate mechanism that catches those, and it runs later, on the proposed order rather than on the file.
Both can fire on one upload. When they do, this screen comes first - it is certain, and it is the only one of the two that can run before the scanner is called at all.

Notes for implementation
Always asked. Every receipt added to an existing order opens dialog 1, from the Attachments filmstrip or by drop, on desktop and phone. Attach only stores the file and nothing else. A file whose hash matches one already on this order goes to 3c instead.
Dialog 2 comes after the reading. Compare reads the receipt first; if its vendor is not the order's vendor (matched by alias, as a scan matches vendors), or its total is more than 25% away from the order's, dialog 2 replaces the comparison. Attach only is the primary there. Compare anyway opens the comparison as normal.
Nothing changes until Apply. Cancel on the comparison keeps the file attached and leaves the lines as they were. The order is not marked as validated.

Notes for implementation
Item lines only. Vendor, date, totals and reference are not compared. Lines are paired by normalised name, then by amount; a pair with the same amount and a different name is a name difference, not two lines.
Four line cases, and the receipt wins by default in each. On both, price or quantity differs: Order / Receipt, Receipt picked. On both, name differs: the same choice. Only on the receipt: ticked, so it is added. Only on the order: unticked, so it is removed. The amount column shows the result, with the value being replaced struck through beneath it, or the whole amount struck through for a line that goes.
Only the differences are listed. Lines that match are counted under the list, not repeated. When nothing differs, the comparison is skipped: the order is marked as validated and the green banner says so (8). The line under the list names the matching lines when there are 3 or fewer, and counts them otherwise ("6 lines match the receipt").
Line order - Changed lines first (price, quantity or name), then lines only on the receipt, then lines only on the order. Within each group, the order's own line order; receipt-only lines in receipt order.
Left out reads as struck through. Any line that will not be in the result has its amount struck through (sp-void): an unticked order-only line, and an unticked receipt-only line too.
Accept all from receipt sets every line back to its default, after the user has changed some. There is no bulk "keep the order"; that is Cancel.
The button counts the changes. "Apply 4 changes" follows the lines as they are picked: a line set to Order, or a receipt-only line unticked, drops out of the count. At zero it reads "Mark validated" (7). The Totals pill follows 3a: green "Totals match" when After changes equals On the receipt, otherwise the amber pill (sp-pill[data-state="progress"], the same pill as an in-progress status) with the gap and its direction, "381,00 kr. more than the receipt" or "less than". A gap does not block Apply.
When things are written - Attach only behaves as any attachment in 1d: the file is saved with the order. Compare stores the file on the order at once, since it has to be read; Cancel therefore leaves it attached. Apply writes the line changes and the Validated marker at once - Compare is only offered when the order has no unsaved changes (6), so there is nothing else to save with it.

Notes for implementation
Phone - The same rows. Below 900px the Order / Receipt choice moves under the line's subtitle, as the line editor's fields do in 1c; the amount stays at the trailing edge. Totals collapse into the save bar.
