1a Order - read view
Same 2fr / 1fr skeleton as the edit screen, so switching between reading and editing moves nothing. Row actions and Add item drop away, fields become label and value rows, status becomes a row in Order details, and the rail ends with Delete order and Edit order; Duplicate is an icon in the Totals head.
Notes for implementation
Intent - The read view exists so the common case - looking something up - costs nothing. It shares the edit screen's grid exactly, so entering edit changes controls, never positions. Build both from one layout component.
Product link - A line with a product link shows its name as a link, opening the product page in a new tab (Hay - Palissade chair). A line without one shows plain text. Only the name is the link; the row itself does not open anything. On touch a tap on the name opens the page the same way. In edit mode (1b, 1c) the name is always plain text, link or not, so a click on a row edits it rather than leaving the page.
Vendor and category link to their orders - The vendor opens the order list filtered to that vendor, /orders?vendor=indbo-mobler; a category opens it filtered to that category, /orders?category=decor. The same routes as "Open in the order list" on Vendors and categories, with the filter chip visible and removable. With several categories, each name is its own link, separated by commas. They are plain links in the app's link colour and open in a new tab like any other. Read view only: in edit the same rows are fields.
Field order - The rows follow the edit screen's field order (1d): Vendor, Date, Kind, Status, the status date, Validated, Categories, Reference, Statistics, Note. Discount and shipping are in Totals.
Validated - Shown only when the order has been checked against a receipt (3d), with the date it was applied. Read only: it is not a field in 1d.
Note - Shown only when the order has a note; an order without one has no Note row. The text sits in a full-width well (the bordered box inside a card, no ground) at regular weight, as the user typed it, line breaks kept.
Watch out - Do not render inputs as disabled fields here. Values are text. A page full of greyed-out inputs reads as broken permissions, and it doubles the DOM for no gain.
Desktop vs mobile - Below 900px the rail moves above the item list, collapsed to a summary line (1d, Responsive reference 18a). Attachments stay a horizontal filmstrip on both - it is the one place sideways scroll is correct, because a receipt strip has no meaningful order.
Duplicate - Duplicate opens the copy as the row menu does (8a). It is rarely used, so it is an outline icon button at the right of the Totals card head: copy (tip "Duplicate", label "Duplicate order"). The footer is the split pair Delete order and Edit order, Edit order the one primary on the right, Delete order outline in the danger colour. The Totals card moves with the rail: below 900px it is in the rail above the items, which is how the phone reaches it.
Easy to get wrong - Edit, Duplicate and Delete belong in the page, never the top bar (global rule 1). The top shell is shared and locked.

1b Desktop - edit an item in place
The pencil turns the row into a form without moving it in the list. Same fields as the mobile sheet: quantity stepper, unit price, retail price, line total. Enter saves, Escape cancels, Cmd/Ctrl+Enter saves and opens the line below. The photo lives in the open row: the thumbnail is the control - clicking it replaces the image, a file can be dropped straight onto it, and Remove sits underneath. Lines with no photo show a dashed tile.
Notes for implementation
Intent - Editing a line happens next to its neighbours because that is what makes the edit correct - you fix a quantity by reading the line above it. The row becomes a form and does not move.
Product link - Optional, per line. The link button at the end of the Item field opens a Product page field directly under it and focuses it. Pressed again while the field is empty, it closes it; while the field holds a link, it only focuses the field, so a link is never hidden. Its label follows: "Add a product link" without one, "Edit product link" with one. A line that already has a link opens with the field showing: 1b draws a line without one, the mobile sheet (1c) a line with one.
Product link - validation - On blur and on save, as every field (c3). An address typed without a scheme ("hay.dk/palissade-chair") is valid and saved with https:// in front. Anything still not a web address turns the field red with "Not a link." under it, and the line does not save until it is fixed or cleared. Try it in 1b: type a word and leave the field.
Product link - saving - The address is cleaned when it is saved, as a bookmark's is: tracking parts such as utm_ and fbclid are removed, and a missing https:// is added.
Product link - copies - A copy of an order keeps each line's link, in every way of copying: Home's Copy an order, the create screen's, and an order's own Duplicate.
Product link - clearing - Emptying the field and saving removes the link: the name in the read view (1a) goes back to plain text, and the editor opens with the field closed next time.
Watch out - Only one row is open at a time; opening another closes the first and keeps its changes in the order draft. The line is never saved to the server on its own - the order save is the only write.
Watch out - Line total is computed and read-only. Do not make it editable "for convenience" - two sources for one number is how totals start disagreeing with receipts.
Desktop vs mobile - This inline expansion is desktop only. On a phone the same fields open in a bottom sheet (1c), because in one column "expands in place" and "takes over the screen" are the same thing. Same fields, same order, same validation - one form component, two containers.
The Add item row keeps the handle's space only where the rows have handles. On a phone the rows have none (1c), so the add row has no spacer and its + lines up with the photos above it.
The open editor has no drag handle. Its photo spans the row's handle, gap and photo, so it starts on the row's handle line and the Item label starts on the rows' title line. The sheet (1c) uses the same 70px photo.
Easy to get wrong - Discoverability. A row must never look inert: pointer cursor, hover fill, and a pencil at the right edge. All three, not one. On touch there is no hover and no pencil: the whole row opens the sheet (1c).

1c Mobile
The rail becomes the bottom of the page. Items lead, attachments scroll sideways, details collapse into one folded section. Total and Save live in a fixed bar so they're reachable without scrolling.
Notes for implementation
Intent - The phone is the capture device, so this layout assumes one hand and a receipt in the other. Items lead because that is the work; details fold away.
Watch out - The details section is collapsed by default with a summary line of its categories, kind and reference ("Decor · Expense · SPENDLY-447"), as drawn. Collapsed must still tell you what is inside, or it reads as an empty accordion.
Watch out - 44px minimum on every target, including the row itself and the sheet buttons. Row density in Settings does not apply here - compact affects list rows on desktop only.
Desktop vs mobile - This is not the desktop layout at a smaller width. Fields were removed, not shrunk: vendor and amount on line one, then the date and item count with the saving under the amount (Order list 2i). Reference, status and category are on the order itself. Anything else lives one level deeper. Do not reintroduce columns to "use the space".
Reorder is a mode, not an action - the same mode the saved-views card uses. Tapping it turns each row into a reorder row: the drag handle appears at the leading edge and an up and a down button at the trailing edge, both required, since drag is awkward on touch inside a scrolling list and the buttons are the accessible path (see 1d). The button becomes Done, which leaves the mode. The moves are changes to the order like any other: they wait for the order's Save, as an explicit position on each line rather than a sort order (1b). Nothing else about the row changes: same height, same content, same 44px targets.
Easy to get wrong - Sticky save on iOS. The save bar must sit above the keyboard and the home indicator - use dynamic viewport units and safe-area insets, or it ends up under both.

1d Edit order
Details and totals in the 1/3 rail, items and attachments in the wide column. Attachments grow sideways as a filmstrip, so the rail never out-runs the items list.
Notes for implementation
Intent - The screen this whole exercise produced. The header moved into the rail so the item list starts at the top of the page and owns the width; nearly every session is adjusting lines.
Watch out - The rail must stay shorter than the item list. If it grows past it, the page scrolls for the rail's benefit and the original problem is back in a new form. Attachments are below the items for exactly this reason - anything new in the rail has to displace something, not extend it.
Watch out - Reorder needs both the drag handle and the up/down buttons. Drag is unusable with a keyboard and awkward on touch inside a scrolling list; the buttons are the accessible path. Order persists as an explicit position field, never derived from a sort.
Adding a receipt - A file added to Attachments asks whether to compare it with the order's lines (3d).
Leave out of statistics - A per-order flag, off by default, stored as excludeFromStats. When on, the order is skipped by every figure, chart, breakdown and limit on Statistics and Home, including the Amount facet's percentile ends. It is still listed, searchable, filterable, exported and counted in the order list's own toolbar total. Status is unaffected: a Delivered order left out is still Delivered. The read view (1a) adds a row Statistics reading Left out only when the flag is on, after Reference and before Note, so Note stays last; an included order has no such row. The same switch is on the new-order form and the form after a scan (Order create). A copy of an order starts with the switch off, whatever the original: the copy is a new purchase, and the person decides again.
Status - A select, not a fixed set. Statuses are custom per user, set up in Settings: their names, how many there are and their order differ from one user to the next. The options are that user's statuses in their Settings order; the trigger shows the current one. Draft, Ordered, Delivered, Returned and Cancelled here are example data, and no status name is special in code. Same combobox as Vendor and Kind (c5).
Status date - Each status is mapped to a date in Settings: either the order's Date, or a date of its own. A status mapped to the order's Date (Ordered in this example) shows nothing extra. A status with its own date shows a date field under Status, labelled with the status name. Date only, no time. Try it: change the status in 1d.
Changing the status - Picking a status that has no date yet fills in today and says so under the field, so the common case costs nothing and a delivery that happened yesterday is one edit. Picking a status that already has a date (switching back to Delivered after trying Returned) restores the saved one, not today. Nothing is written until Save, like every other field here.
Status date - validation - On blur and on save (c3): a Delivered or Returned date before the order's Date is an error, and the order does not save until it is fixed. A future date is allowed. Same date format and picker as Date above.
Read view - 1a shows the date of the current status as its own row under Status, labelled with the status name ("Delivered 09/08/2026"). A status mapped to the order's Date has no extra row.
Watch out - Crossing a category limit shows the amber notice and the save proceeds. Keep that check out of the validation layer entirely - once it shares a code path with required fields, it eventually starts blocking.
Desktop vs mobile - Below 900px this becomes 1c: rail collapses to a section above the items, inline expansion becomes a sheet. The sticky save bar survives the transition and is the one element that must never be scrolled away.
Easy to get wrong - Sticky positioning here is relative to the content column, which is the page's only scroll container - not the viewport. Get the shell right first (see the README) or every sticky element in the app misbehaves.
