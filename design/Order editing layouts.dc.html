1a Order — read view
Same 2fr / 1fr skeleton as the edit screen, so switching between reading and editing moves nothing. Row actions and Add item drop away, fields become label and value rows, status becomes a pill in the items header, and the rail ends with Duplicate, Delete and Edit order.
NOTES FOR IMPLEMENTATION
Intent — The read view exists so the common case — looking something up — costs nothing. It shares the edit screen's grid exactly, so entering edit changes controls, never positions. Build both from one layout component.
Watch out — Do not render inputs as disabled fields here. Values are text. A page full of greyed-out inputs reads as broken permissions, and it doubles the DOM for no gain.
Desktop vs mobile — Below 900px the rail moves under the item list. Attachments stay a horizontal filmstrip on both — it is the one place sideways scroll is correct, because a receipt strip has no meaningful order.
Easy to get wrong — Edit, Duplicate and Delete belong in the page, never the top bar (global rule 1). The top shell is shared and locked.

1b Desktop — edit an item in place
The pencil turns the row into a form without moving it in the list. Same fields as the mobile sheet: quantity stepper, unit price, retail price, line total. Enter saves, Escape cancels, Cmd/Ctrl+Enter saves and opens the line below. The photo lives in the open row: the camera badge opens upload / take / paste / pick / remove, and a file can be dropped straight onto the thumbnail. Lines with no photo show a dashed tile.
NOTES FOR IMPLEMENTATION
Intent — Editing a line happens next to its neighbours because that is what makes the edit correct — you fix a quantity by reading the line above it. The row becomes a form and does not move.
Watch out — Only one row is open at a time; opening another closes the first and keeps its changes in the order draft. The line is never saved to the server on its own — the order save is the only write.
Watch out — Line total is computed and read-only. Do not make it editable "for convenience" — two sources for one number is how totals start disagreeing with receipts.
Desktop vs mobile — This inline expansion is desktop only. On a phone the same fields open in a bottom sheet (1c), because in one column "expands in place" and "takes over the screen" are the same thing. Same fields, same order, same validation — one form component, two containers.
Easy to get wrong — Discoverability. A row must never look inert: pointer cursor, hover fill, and a pencil at the right edge. On touch there is no hover, so the pencil is permanently visible. All three, not one.

1c Mobile
The rail becomes the bottom of the page. Items lead, attachments scroll sideways, details collapse into one folded section. Total and Save live in a fixed bar so they're reachable without scrolling.
NOTES FOR IMPLEMENTATION
Intent — The phone is the capture device, so this layout assumes one hand and a receipt in the other. Items lead because that is the work; details fold away.
Watch out — The details section is collapsed by default with a summary line ("Indbo Møbler · 12 Aug · Received"). Collapsed must still tell you what is inside, or it reads as an empty accordion.
Watch out — 44px minimum on every target, including the row itself and the sheet buttons. Row density in Settings does not apply here — compact affects list rows on desktop only.
Desktop vs mobile — This is not the desktop layout at a smaller width. Fields were removed, not shrunk: vendor and amount on line one, date/items/status on line two, category on line three. Anything else lives one level deeper. Do not reintroduce columns to "use the space".
Easy to get wrong — Sticky save on iOS. The save bar must sit above the keyboard and the home indicator — use dynamic viewport units and safe-area insets, or it ends up under both.

1d Edit order
Details and totals in the 1/3 rail, items and attachments in the wide column. Attachments grow sideways as a filmstrip, so the rail never out-runs the items list.
NOTES FOR IMPLEMENTATION
Intent — The screen this whole exercise produced. The header moved into the rail so the item list starts at the top of the page and owns the width; nearly every session is adjusting lines.
Watch out — The rail must stay shorter than the item list. If it grows past it, the page scrolls for the rail's benefit and the original problem is back in a new form. Attachments are below the items for exactly this reason — anything new in the rail has to displace something, not extend it.
Watch out — Reorder needs both the drag handle and the up/down buttons. Drag is unusable with a keyboard and awkward on touch inside a scrolling list; the buttons are the accessible path. Order persists as an explicit position field, never derived from a sort.
Watch out — Crossing a category limit shows the amber notice and the save proceeds. Keep that check out of the validation layer entirely — once it shares a code path with required fields, it eventually starts blocking.
Desktop vs mobile — Below 900px this becomes 1c: rail collapses to a section above the items, inline expansion becomes a sheet. The sticky save bar survives the transition and is the one element that must never be scrolled away.
Easy to get wrong — Sticky positioning here is relative to the content column, which is the page's only scroll container — not the viewport. Get the shell right first (see the README) or every sticky element in the app misbehaves.
