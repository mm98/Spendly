18a Responsive reference — working layouts, not descriptions
Every other page in this set is a static canvas drawn at one width, so there is nothing in them to infer breakpoint behaviour from. This page is the exception: the layouts below genuinely respond, and each one is annotated with the CSS that makes it happen. Read this page as the implementation and the others as the visual target.
NOTES FOR IMPLEMENTATION
Container queries, not media queries. Every rule below keys off the width of the element's own container (container-type: inline-size on the layout wrapper), not the viewport. This matters because the same components sit in a 1fr main column, a 360px rail, and a 400px panel — a viewport query gets all three wrong at once. Media queries are correct for exactly two things: the shell breakpoint that turns the sidebar into a tab bar, and the print sheet.
Each demo below is inside its own resizable frame. Drag the canvas narrower, or resize the browser, and each one crosses its own threshold independently — which is the whole point of container queries and impossible to show in a static mockup.
The thresholds are container widths, not viewport widths. 900 on a main column inside a 248px sidebar and 48px padding means a viewport of roughly 1244. Don't translate them — put the query on the container and the numbers work out.
Four thresholds exist in the entire product: 1280 (a left rail leaves the layout), 900 (two columns become one), 640 (phone treatment: rows become cards, dialogs become sheets, field grids collapse), and the shell's own 640 viewport query. Nothing else. A fifth threshold is a design change, not an implementation detail.

CSS
.order-layout { container-type: inline-size; display: grid; grid-template-columns: minmax(560px, 1fr) 360px; gap: 24px; align-items: start; } @container (max-width: 900px) { .order-layout { grid-template-columns: 1fr; gap: 14px; } .order-layout > .rail { order: -1; } .rail-full { display: none; } .rail-summary { display: flex; } }
order: -1 is the whole trick. The rail moves above the item list, not below it. A form appended under a list of forty lines is somewhere nobody scrolls to.
The rail collapses to a summary line rather than staying expanded: same element, two children, one shown at a time. The summary states its own contents ("Indbo Møbler · 12 Aug · Received") so a closed section is never a mystery.
minmax(560px, 1fr) is deliberate. The main column refuses to go under 560px; the grid overflows its container instead, which surfaces the problem in development rather than silently crushing the item rows.

CSS — TWO INDEPENDENT THRESHOLDS
@container (max-width: 1280px) { /* rail leaves */ .list-layout { grid-template-columns: minmax(0, 1fr); } .facets { display: none; } .facet-trigger { display: flex; } } @container (max-width: 640px) { /* rows → cards */ .row-table .head { display: none; } .row-table .r { grid-template-columns: minmax(0, 1fr) auto; border: 1px solid #e6e4dc; border-radius: 12px; } .row-table .r .hide-m { display: none; } .row-table .r .m2 { display: block; grid-column: 1 / -1; } }
The two thresholds are independent. At 1000px the facets are a drawer but the table is still a table. Chaining them into one breakpoint is what produces the cramped intermediate state.
One row markup, two presentations. The desktop cells carry .hide-m; the phone lines carry .m2 and are in the DOM the whole time, hidden. Two separate row components drift apart within a sprint.
Vendor is the fluid cell; amount stays 120px. Fixed columns must never add up to more than the container, so two intermediate queries drop items at 1040 and category at 880 — before the grid runs out of room. A starved minmax(0, 1fr) silently collapses a cell to zero rather than overflowing, which is the failure mode to watch for.

CSS — NO QUERY AT ALL
.order-cards { display: grid; grid-template-columns: repeat(auto-fill, minmax(280px, 1fr)); gap: 16px; } /* Statistics — 12 columns, every card a whole number of them */ .stats-grid { container-type: inline-size; display: grid; grid-template-columns: repeat(12, 1fr); gap: 16px; } .kpi { grid-column: span 3; } @container (max-width: 1280px) { .kpi { grid-column: span 4; } } @container (max-width: 900px) { .kpi { grid-column: span 6; } } @container (max-width: 640px) { .kpi { grid-column: span 12; } }
Order cards need no query. auto-fill with a 280px floor reflows at every width on its own. Adding breakpoints to a grid that already works is the most common unnecessary complexity here.
Statistics is the opposite case and does need queries, because the span values must stay divisors of 12 for rows to close. 3 → 4 → 6 → 12 are the only legal steps; anything else leaves the gap in the middle of a row.
Verify Statistics at 1280, 1440 and 1920 specifically — those are the widths where a wrong span shows as a half-filled row.

Both frames above are 420px, so both are past 640 and both have collapsed — regardless of how wide the browser window is. Widen the window as far as you like and they stay collapsed; the same field grid in a 1fr main column does not. That is the container query doing its job, and it is the behaviour a viewport query cannot produce.
The computed cell is replaced, not moved. Two elements, one shown at a time — a read-only field becomes a total line, because a box you cannot type into is a target that does nothing.
Only padding changes for touch. 42px to 46px clears the 44px minimum. Type sizes never change between desktop and phone.

HOW TO USE THIS PAGE WHEN BUILDING
Build the container-query wrappers first — the four shapes above, as four layout components. Every screen then picks one and fills it. Screens that hand-roll their own grid are how a fifth threshold appears.
The static mockups are the visual target at desktop width only. They are drawn at one width with fixed pixel values and no queries, so nothing about narrow behaviour can be read off them. Where a mockup and this page disagree about a narrow layout, this page wins.
Side-by-side panels in the other files are annotation, not layout. The comparison columns headed "1 — pick a file", "empty" / "loaded", or "light" / "dark" are never on screen together. Don't build a responsive row out of them.
Test at container widths, not viewport widths. Resize the layout wrapper in isolation — a component that only works at one page width will pass a viewport test and fail in the rail.
ACCEPTANCE, PER SCREEN
At each of 1440 · 1280 · 1024 · 900 · 768 · 640 · 390: no horizontal scroll except the two places it is named above; no text under 11px; every target 44px or more below 640; no element overlapping another; and the sticky save bar reachable without the keyboard covering it.
The two widths that catch the most: 1024, where a rail has left but the table has not yet become cards, and 390, the narrowest phone that matters.
