18a Responsive reference - working layouts, not descriptions
Every other page in this set is a static canvas drawn at one width, so there is nothing in them to infer breakpoint behaviour from. This page is the exception: the layouts below are the real CSS running at the widths named, and each one is annotated with the CSS that makes it happen. Read this page as the implementation and the others as the visual target.
NOTES FOR IMPLEMENTATION
Container queries, not media queries. Every rule below keys off the width of the element's own container (container-type: inline-size on the layout wrapper), not the viewport. This matters because the same components sit in a 1fr main column, a 360px rail, and a 400px panel - a viewport query gets all three wrong at once. Media queries are correct for exactly two things: the shell breakpoint that turns the sidebar into a tab bar, and the print sheet.
Every value here is copied from the screen it illustrates, never invented. This page owns the breakpoints and the CSS; it owns nothing else. Column order, checkbox width, chip geometry, date format, amount format and thumbnail size all come from 2b and 1a. If a value here disagrees with the screen, this page is stale - the screen wins.
Hiding a cell needs the hide rule to win. A cell centred with an inline display: flex can never be hidden by a container query, because inline style beats a stylesheet rule. Put the centring in the class and keep display under the query's control - otherwise the header narrows while the rows keep their cell, and the row wraps to a second line.
Each demo below is inside its own resizable frame. Drag the canvas narrower, or resize the browser, and each one crosses its own threshold independently - which is the whole point of container queries and impossible to show in a static mockup.
The thresholds are container widths, not viewport widths. 900 on a main column inside a 248px sidebar and the page's own 16px inset means a viewport of roughly 1180. Don't translate them - put the query on the container and the numbers work out.
Four thresholds exist in the entire product: 1280 (a left rail leaves the layout), 900 (two columns become one), 640 (phone treatment: rows become cards, dialogs become sheets, field grids collapse), and the shell's own 640 viewport query. Nothing else. A fifth threshold is a design change, not an implementation detail.

The two thresholds are independent. At 1000px the facets are a drawer but the table is still a table. Chaining them into one breakpoint is what produces the cramped intermediate state.
One row markup, two presentations. The desktop cells carry .rr-hide-m; the phone lines carry .rr-m2 and are in the DOM the whole time, hidden. Two separate row components drift apart within a sprint.
Vendor is the fluid cell; amount stays 120px. A starved minmax(0, 1fr) silently collapses a cell to zero rather than overflowing, which is the failure mode to watch for.

Order cards need no query. auto-fill with a --card-min-w floor (280px) reflows at every width on its own: one column below 572px, two from 572, and as many as fit above. Adding breakpoints to a grid that already works is the most common unnecessary complexity here.
Statistics states its tracks instead. Its four figure cards sit one per track in .sp-stats, a four-column grid, because a figure card has a floor no auto-fill can express: below about 240px the figure and its sparkline stop being readable together. The tracks step with the shell rather than the content.
Verify Statistics at 1280, 1440 and 1920 specifically - those are the widths where a four-track row either fits or leaves a card short of its floor.

Both frames above are 420px, so both are past 640 and both have collapsed - regardless of how wide the browser window is. The computed cell is replaced, not moved. Two elements, one shown at a time - a read-only field becomes a total line, because a box you cannot type into is a target that does nothing.
Only padding changes for touch. 42px to 48px clears the 44px minimum. Type sizes never change between desktop and phone.

HOW TO USE THIS PAGE WHEN BUILDING
Build the container-query wrappers first - the four shapes above, as four layout components. Every screen then picks one and fills it. Screens that hand-roll their own grid are how a fifth threshold appears.
The static mockups are the visual target at desktop width only. They are drawn at one width with fixed pixel values and no queries, so nothing about narrow behaviour can be read off them. Where a mockup and this page disagree about a narrow layout, this page wins.
Side-by-side panels in the other files are annotation, not layout. The comparison columns headed "1 - pick a file", "empty" / "loaded", or "light" / "dark" are never on screen together. Don't build a responsive row out of them.
Test at container widths, not viewport widths. Resize the layout wrapper in isolation - a component that only works at one page width will pass a viewport test and fail in the rail.
ACCEPTANCE, PER SCREEN
At each of 1440 · 1280 · 1024 · 900 · 768 · 640 · 390: no horizontal scroll except the two places it is named above; no text under 11px; every target 44px or more below 640; no element overlapping another; and the sticky save bar reachable without the keyboard covering it.
The two widths that catch the most: 1024, where a rail has left but the table has not yet become cards, and 390, the narrowest phone that matters.
