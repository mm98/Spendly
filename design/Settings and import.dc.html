11a Settings
Ten panes, one per thing that changes how the rest of the app behaves. A second navigation inside the page lists them, and the pane itself is one column of cards at a reading width - not the list-and-rail split the record screens use, because nothing here is being looked up against anything. Nothing saves by itself: each card has its own save, and only the card you touched goes dirty.
Notes for implementation
A very long status name ends in an ellipsis in this list (.sp-pill--truncate), so its row keeps its height; the full name is in the edit field. This is the one place a pill truncates.
Limit alerts is its own pane, between Lists and Statuses: the in-app and email switches and "Tell me early, at" (8b).
The language and region setting writes dates, times and numbers - the preview shows all three - and every figure in the app follows it, amounts included.
The profile photo is a FileDrop: drop an image on the round mark, or use Upload a photo. With no photo the mark is the initials on --green-3, round, as in the sidebar.
A status with orders on it cannot be deleted. The delete control is absent on those rows, not disabled - reassigning the orders is what makes it appear. Every row has the pencil; a row with no orders also has the trash. Rename, reorder and delete all wait for the save bar, like every change on this page. Its tone is one of the four the pill component has, picked as the pill the list will draw.
Order views in the menu offers 2, 3, 4, 5, 6, 8, 10 - same numeric-combobox pattern as Rows per page (tabular figures, unit word beside the value, chevron right). Views beyond the chosen count collapse into the "N more in Orders" row in the sidebar. The list is always the first N; when the open view is one of the rest, that row is marked current and nothing else changes (9e).
The save bar is sticky to the bottom of the content column. Each card saves on its own, so the bar names which one is dirty - and with a pane this long the dirty card is usually scrolled off screen by the time you want to save it. A bar that scrolls away leaves the only exit from an edit somewhere the user has to hunt for. It appears when something is dirty and is absent otherwise, matching the edit screen in 1d.
Note on the frame
The 1180px shell below is presentation only - a stand-in for a viewport, so the screen reads in context on this page. It is not a width the app has. In the app the shell fills the browser edge to edge: sidebar 248px fixed, content column fluid, exactly as 9a defines it.
Inside the content column, three widths do the work: the section nav is 208px fixed, the divider beside it is a hairline, and the card column is fluid with a 640px cap. Past 640px the cards stop growing and the slack falls to their right - a 42px input stretched across a 1920px screen looks like an error (15a). Below roughly 900px the section nav becomes a select above the cards, and the cap stops binding because the column is already narrower than it.

Notes for implementation
The pickers and the warning are not shown at rest. The card opens as one secondary button. Pressing it reveals the two choices, the warning and the confirm pair - so a destructive action takes two deliberate presses without a dialog, and the settings page never carries a permanent red panel.
Filling is determinate. The count is known before it starts, so the bar shows real progress and a figure. There is no cancel: a half-filled account is the failure state, and stopping on purpose would produce it deliberately.
Done and Failed both say what now exists. Failure keeps the partial rows rather than rolling back, and says how many - the user needs to know what is in their lists, and this is demo data, so a partial set costs nothing.
Red here is correct. This is the one control in Settings that destroys data, which is why the warning is red rather than amber and why the confirm names the consequence instead of saying OK.

Notes for implementation
Five states, one card. Resting shows what is installed and offers the check. Checking disables the button and swaps its label for a verb. Up to date and Update available both answer the question that was asked, so the result sits in the card rather than in a toast - a toast would be gone before the user looked back. The notice that a newer version is running on the server (6d) is a separate case: nobody asked for it, so it comes to the user and stays until answered. Check failed keeps the version line intact, because a failed check says nothing about what is running.
Checking holds for at least 2 seconds, even when the answer arrives sooner. A check that returns in 80ms flashes the spinner and lands on a result the user did not see appear - it reads as the button having done nothing. Hold the state, then swap. The version line stays in place throughout. Its hint shows at rest and while checking; a result takes the hint's place, at the same height, so nothing below the card moves.
Only state 4 has a primary button. Updating is the one action here with a consequence, and it is the only state where the button changes what it does rather than repeating the check.
The result does not persist. States 3 to 5 hold until the card leaves the screen, then the card returns to resting. A stale "up to date" is worse than no answer.
Amber informs, it does not block. An available update is a fact, not a warning: nothing about the app stops working, and the user may keep the version they have.
