5a Vendors — overview
The list, and a read-only panel for whatever is selected. Nothing on this screen is editable: the panel answers “what is this vendor and how much have I spent there”, and Edit opens the page in 5c.
NOTES FOR IMPLEMENTATION
The panel is read-only, deliberately. Editing is a page (5b, 5c), the same shape an order uses, so there is one form mechanism in the app rather than two. A 400px panel cannot hold a sticky save bar, and a form whose Save scrolls away is the problem that moved the order header out of the page top in the first place.
Selecting a row is not navigation. It fills the panel and pushes ?vendor=indbo onto the URL, so a selection survives reload and can be linked. Clicking Edit navigates to /vendors/indbo/edit.
The panel never collapses. With nothing selected it shows the roll-up (5g), so the column width is constant and the list never jumps under the cursor.
The duplicate notice is advisory. It appears when a scan created a vendor whose normalised name is within 0.85 of an existing one. Nothing is merged automatically — see 5l.

5b Vendors — create
Reached from New vendor in the toolbar, or from a scan that found a name it does not know. A page at /vendors/new, with the same rail and sticky bar an order uses.
NOTES FOR IMPLEMENTATION
Name is the only required field. Everything else has a working default, so a vendor created mid-scan costs one field. Save stays enabled. Pressing it with an empty name runs validation and marks the field — the button never explains what is missing better than the field itself can.
Create and edit are the same page. One route component, one form, one rail. The differences are the crumb, the primary label, and whether the delete card is present. Do not build them separately — they drift.
Duplicate names are checked on blur, not on submit. A name within 0.85 of an existing vendor shows an amber notice under the field offering that vendor instead. It does not block: two shops can genuinely share a name.
Created from a scan, it returns to the scan. The page carries the return in its route state and the new vendor is selected on arrival back — never dropping the user on the vendor list with their receipt abandoned.
Aliases are on this page, because creating from a scan is when the first one matters most. The receipt name that triggered the create is pre-filled as an alias — the one moment the app knows it. Forcing a second trip to the edit page to keep it means the next receipt from the same shop creates another duplicate.

NOTES FOR IMPLEMENTATION
Dirty tracking is per field against the loaded values. Reverting a field by hand clears its flag; when none remain the save bar disappears. Whitespace-only edits do not count.

5h The identity mark
One control, two sources. A vendor derives initials and colour from its name; a category carries a picked icon and a picked colour. Both render at the same sizes in the same places, so a list row does not care which kind it is showing.
NOTES FOR IMPLEMENTATION
Sizes are fixed, not a scale. 26px in a chip or field, 34px in a list row and the summary card, 42px on a form and the detail header, 56px nowhere yet. Glyph is 52% of the tile; type is 38% — the ratio that stops a two-letter mark crowding its edges.
Vendor initials: first letter of the first two words, uppercased, accents kept (Ø stays Ø). One word gives one letter — not two letters from the same word. Digits and punctuation are skipped, so “7-Eleven” is E.
Vendor colour is derived, then overridable. A stable hash of the name picks from the same eight swatches a category uses, so a vendor created twice looks the same both times. Once a user picks one, the hash is never consulted again — store the override, not a flag.
A vendor never has a photo. Always initials. Do not fetch favicons or logos, however tempting the website field makes it.
The glyph flips to dark ink above L 75. One threshold, computed from the swatch, not a per-colour lookup table.
Never shrink it to make a row fit. A row drops columns before its mark changes size — see 5m.

5i Aliases — the names on receipts
A vendor has one name you recognise and any number of names its receipts actually print. The alias list is what lets a scan file a receipt without asking.
NOTES FOR IMPLEMENTATION
Matching is normalised, not literal. Case-folded, accents stripped, punctuation and legal suffixes removed (A/S, ApS, Ltd, GmbH), whitespace collapsed. “INDBO MØBLER A/S” and “indbo møbler” both reach the same vendor without either being stored twice.
An alias can be a name, a domain or a VAT number. One field, three kinds — the scan tries all three against whatever it read. Do not split them into three inputs; the user does not think of them as different.
Aliases are unique across all vendors. Adding one already claimed elsewhere shows which vendor holds it and offers to move it, because two vendors matching one receipt string is how a scan silently files things wrongly.
Merging moves aliases. The source vendor’s name becomes an alias of the target, along with everything it already held — see 5l. That is what stops the same duplicate reappearing on the next receipt.
Removing an alias does not touch existing orders. They keep their vendor. It only changes what future scans match.
The green chip is the one that matched most recently, so a user checking why a receipt landed here has an answer without opening anything.

5j The monthly limit
One amount on a category, applied to every month. The number itself is a plain amount field — everything interesting is what it renders as, and what it deliberately does not do.
NOTES FOR IMPLEMENTATION
It is one value, not a series. No per-month editing, no history of changes. A series invites a calendar, a “copy last month”, and a question about which month’s limit a historical comparison should use — none of which was asked for. If per-month planning is ever wanted, that is a new concept with its own screen, not a change to this field.
Empty means no limit. Zero means nothing should be spent here. They are different, and both are valid. If you do not want the distinction, reject zero — do not silently convert it.
The pace marker exists because the limit is flat and the month is partial. “3.400 of 6.000” on day 20 is unreadable without it. Position is day / daysInMonth; it is a reference line, never a threshold, and never coloured red.
Over the limit fills amber and caps the bar at 100%. A capped bar cannot express how far past it went, so the overage is always stated in words beside it. On a phone there is no adjacent column, so that sentence goes underneath — never omitted.
A list row splits the amber into two segments. The part up to the limit is #d3b98a; the overage beyond it is #e2d3ae, one step paler, so the row shows both how much the limit was and how far past it went inside the same 100% track. A panel or a form has room for the sentence instead, and uses the single fill.
Four fills in total, and no others. #1d4d33 under the limit, #d3b98a up to a limit that has been passed, #e2d3ae for the overage segment, and the bare #f7f6f2 track when no limit is set. Red never appears on a limit bar — it would read as a blocked save.

5k The icon picker
Categories only. A fixed library, searchable, rendered in the category colour — the same control 14a specifies as SwatchPicker with an 8-column grid.
NOTES FOR IMPLEMENTATION
A fixed set, never an upload. Every glyph has to survive four contexts — a 26px tile with a white glyph, the same tile with dark ink, a 12px chart bar, and a chip — and an uploaded image satisfies none of them. This is a design decision, not a limitation to relax later.
Icons are stored by stable key, not by index or by path. Reordering the library or adding to it must never change what an existing category shows.
Search matches names and synonyms. “sofa” finds the seating glyph, “lamp” finds lighting. Without synonyms a fixed library of 80 is unusable, because the user does not know what you called it.
Arrow keys move in two dimensions, not one — it is a grid. Home and End reach the true first and last, and every cell carries an accessible name. A glyph with no name is unusable without sight.
The overflow cell is a count, not an ellipsis. “+64” says how much more there is; “…” says nothing. It expands in place rather than opening a second surface.
Selection is an outline, never a check over the glyph. A tick on top of a 16px icon obscures the thing being chosen.

5l Merge, and moving orders
The two ways a record ends. A vendor merges into another; a category hands its orders over. Both are irreversible, both are confirmed by naming the number of orders that will move.
NOTES FOR IMPLEMENTATION
Merge is vendors only. The source’s orders move to the target, its name and aliases become the target’s aliases, and the source is deleted. Moving the aliases is the important half — without it the next receipt recreates the duplicate.
The comparison shows which value wins per field. The target keeps its own unless the source has one and the target does not. Nothing is silently blended, and the user can see the result before agreeing to it.
Categories reassign rather than merge. There is nothing to combine — a category is a label, so its orders are pointed at another one and it is then deletable. Same dialog shape, different verb.
Not reversible, and the dialog says so. Undo is the pattern everywhere else, but this moves rows across records; write an audit record instead of promising a rollback you cannot do.
Suggested merges are advisory. Normalised name similarity above 0.85, or an identical VAT number. Never merged automatically, at any confidence — the cost of a wrong merge is unrecoverable.
The count is the last thing in the button. “Merge 2 orders”, not “Confirm” — a number the user reads on the button is one they cannot claim not to have seen.

The progress bar is a column, not decoration. It stays at every width and goes full width on the phone, where it becomes the row's primary shape. Over the limit it fills amber and the overage is stated in words underneath — a bar pinned at 100% cannot say how far past it went, and on a phone there is no adjacent column to say it for you.
The panel is why these tables can shed columns at all. Both screens are list-plus-panel (5a), so anything dropped is one click away and still exact. Below 900px the panel becomes a separate view, which is also where the tables become cards — the two changes are the same change.
Same three implementation rules as 2i. Container queries on the list column, not the viewport — this list sits beside a 400px panel, so its width is never the window's. One grid definition shared by header and rows, declared once and overridden per breakpoint. And min-width: 0 on every fluid cell, with the ellipsis triple on every text cell: without it a grid child refuses to shrink below its content and the row overflows instead of truncating.
The identity mark never shrinks and never drops. 34px at every width. It is the fastest way to find a row, and it is the only thing in the row that survives on a phone unchanged.
