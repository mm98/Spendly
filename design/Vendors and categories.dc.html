5a Vendors - overview
The list and nothing beside it. A row opens the vendor for editing in 5c - one click, not two - and the figures that used to sit in a panel here are in that page's rail, beside the fields they describe. This screen finds a vendor and creates one.
Notes for implementation
The overview has no panel. A row opens the edit page (5b, 5c), the same shape an order uses, so there is one form mechanism in the app rather than two - and one click to the thing the screen is for rather than a summary and then a click. The figures live in that page's rail, which is 360px and could never have held a sticky save bar anyway; the save bar spans the form.
The list does not show a vendor's Leave out of statistics default (5l), in rows or cards. It is read on the vendor's page.
A row is a link. Clicking one navigates to /vendors/indbo/edit - it middle-clicks and deep-links like any other, and there is no selected state to survive a reload because selecting is not a thing this screen does.

    • 5b Vendors - create
    Reached from New vendor in the toolbar, or from a scan that found a name it does not know. A page at /vendors/new, with the same rail and sticky bar an order uses.
    Notes for implementation
    Name is the only required field. Everything else has a working default, so a vendor created mid-scan costs one field. Save stays enabled. Pressing it with an empty name runs validation and marks the field - the button never explains what is missing better than the field itself can.
    Create and edit are the same page. One route component, one form, one rail. The differences are the crumb, the primary label, and whether the delete card is present. Do not build them separately - they drift.
    Duplicate names are checked on blur, not on submit. A name within 0.85 of an existing vendor shows an amber notice under the field offering that vendor instead. The same name, compared without case or accents, is an error: two vendors cannot share a name, because a receipt string matching two vendors is how a scan files things wrongly (5h).
    Created from a scan, it returns to the scan. The page carries the return in its route state and the new vendor is selected on arrival back - never dropping the user on the vendor list with their receipt abandoned.
    The image is optional, can be any picture - a logo, a shop front, anything - and its only use is in place of the item photo on this vendor's orders that have none, drawn as an item photo and faded. It is the c17 thumb slot at --mark-large, unchanged. Empty it is the dashed add frame; filled it is .sp-mark--photo, as an item photo slot with Remove beneath it, and choosing a new file replaces it. Validation, sizes, renditions and every place it appears are in 17e. The vendor's own mark stays initials everywhere, with or without an image.
    Aliases are on this page, because creating from a scan is when the first one matters most. The receipt name that triggered the create is pre-filled as an alias - the one moment the app knows it. Forcing a second trip to the edit page to keep it means the next receipt from the same shop creates another duplicate.

    5d Categories - overview
    The same shape as 5a, answering a different question. A vendor list asks how much and how recently; a category list asks what the limit is and how close this month is to it - so its columns lead with the month rather than the year. A row opens the category in 5f.
    Notes for implementation
    The row menu holds every action the edit page does, and only the ones that can run. Open in the order list, Edit, Merge into… and Delete - so a user working down the list never has to select a row first. A vendor with orders shows Archive and no Delete, exactly as its edit page does; nothing lives only in the menu, and nothing lives only in the edit page.
    Same components as 5a, different content. List to an edit page, figures in the page's rail. If you built the vendor screen, this is the same components with a different record type - not a second implementation.
    Over the limit fills amber and states the overage in words. The bar caps at 100%, so it cannot say how far past it went - see 5i. Amber informs; nothing about being over stops the user doing anything.
    The pace marker is a reference line, not a threshold. At day / daysInMonth, it exists because a flat monthly limit is unreadable against a partial month.
    Bookmarks use these categories too. There is one set of categories in the app; a bookmark carries them the way an order does, and the Bookmarks filter in 22b lists the ones bookmarks use. A category typed into a bookmark in 22c lands in this list.
    A category is never archived. Unlike a vendor it is a label the user invented, so there is nothing to keep out of the way - its three exits are rename, merge into another category, and delete, all in 5f. Delete is not gated behind a merge: the field is optional on an order, so a category can be removed outright.

    • URL filters - over the limit, near the limit, has a limit, and a month
    Four filters that exist only in the URL. The page has no control for any of them. flag=over-limit cuts the list to the categories over their limit; flag=near-limit cuts it to the categories at or past the "Tell me early" share of their limit and not over it; flag=limited cuts it to the categories that have a limit; month=2026-08 keeps only the categories with spend in that month, and every figure on the list is measured against that month; a category with no spend in it is not listed. Together they list the categories over their limit in that month, the over test using that month's spend. Either or both arrive from a link.
    Each applied URL filter shows as a removable crumb above the list, the same sp-crumb in sp-filters the order list uses (2b), so the user can see why the list is short and get back to all of it. Removing a crumb drops that parameter. Search and sort keep working.
    flag=limited shows the removable tag "Has a limit", the same sp-crumb as "Over the limit". With no category that has a limit, the list reads "No category has a limit".
    flag=near-limit shows the removable tag "Near the limit", the same sp-crumb as "Over the limit". A category over its limit is not in this list; it is in the over-limit one. When the list is empty it reads "No category is near its limit this month".
    Which links open this list filtered. Needs a look's "N over their limit" opens /categories?flag=over-limit, on Home and on a phone; the toolbar count matches the count on Home. Needs a look's "near its limit" row opens /categories?flag=near-limit. Edit on category on the Monthly limit card (4a) opens /categories?flag=limited. "All N" in Categories this month on Home opens /categories?month=2026-08, so the list holds the same N categories the button counts. A link that shows a number opens a list with exactly that many items; if it cannot, the number is not shown.
    With a month set, the column names it - AUGUST in place of THIS MONTH - and the pace marker goes, since the month is over. The limit column shows the limit as it stands today.
    When nothing matches the list shows its empty state and the crumbs stay. With the over-limit filter it reads "No category is over its limit in August 2026"; with the month filter alone, "No category has spend in August 2026". With no month set the text ends "this month" instead: "No category is over its limit this month". On a phone the crumb row sits above the category cards in 7a (Categories).

    At /categories/new. Reached from New category, from the "Create …" row in any category picker, or from an import that met a value it does not know.
    Notes for implementation
    Name is the only required field. A default icon and the next unused colour are pre-selected, so a category created from a picker costs one field and one Enter.

    5f Categories - edit
    The same page as 5e with the record loaded, at /categories/decor/edit. The limit card gains this month's position against the limit, and the end-of-life card appears.
    Notes for implementation
    Changing the limit is retroactive in display only. The bar and every amber notice recompute against the new number immediately, and nothing already saved is rejected or re-validated. A limit is a fact about a month, not a rule about data.
    The limit is not a series. One amount, applied to every month, with no history of changes - see 5i for why, and for what to do instead if per-month planning is ever wanted.
    Deleting or merging reaches bookmarks as well. Delete takes the label off bookmarks the same way it does off orders, and Merge moves them to the target category. A bookmark keeps its other categories.
    Renaming does not break references. Orders point at an id. The name is display only, so a rename shows up everywhere at once with no migration.
    Delete is offered whatever the count, because a category is optional on an order. Deleting one takes the label off its 64 orders; each keeps whatever other categories it carries, and any left with none is in a state an order is allowed to be in. A vendor is different on both counts: one per order, and required - so the record can be archived but never removed from under it. Without this, a category made by mistake and attached to one order could never be removed without mislabelling that order.
    Three exits, and they do different things. Rename, for a category that should be called something else - orders point at an id, so it reaches every screen at once. Merge, for one that belongs inside another. Delete, for one that should not exist - the label comes off its orders and their other categories stay.
    The confirmation names the consequence, not the count alone. the dialog states "the label comes off 64 orders, 9 of them carry no other category" in its copy, while the button says only Delete category - a count in a destructive button reads as the number of records about to be destroyed. Deleting also removes the limit; nothing about the orders themselves changes but their label.
    Save returns to the list, exactly as the vendor page does. Same route pattern, same return behaviour.

    5h Aliases - the names on receipts
    A vendor has one name you recognise and any number of names its receipts actually print. The alias list is what lets a scan file a receipt without asking.
    Notes for implementation
    Matching is normalised, not literal. Case-folded, accents stripped, punctuation and legal suffixes removed (A/S, ApS, Ltd, GmbH), whitespace collapsed. "INDBO MØBLER A/S" and "indbo møbler" both reach the same vendor without either being stored twice.
    An alias can be a name, a domain or a VAT number. One field, three kinds - the scan tries all three against whatever it read. Do not split them into three inputs; the user does not think of them as different.
    Aliases are unique across all vendors. Adding one already claimed elsewhere shows which vendor holds it and offers to move it, because two vendors matching one receipt string is how a scan silently files things wrongly.
    Merging moves aliases. The source vendor's name becomes an alias of the target, along with everything it already held - see 5j. That is what stops the same duplicate reappearing on the next receipt.
    Removing an alias does not touch existing orders. They keep their vendor. It only changes what future scans match.
    The green chip is the one that matched most recently, so a user checking why a receipt landed here has an answer without opening anything.

    5i The monthly limit
    One amount on a category, applied to every month. The number itself is a plain amount field - everything interesting is what it renders as, and what it deliberately does not do.
    Notes for implementation
    It is one value, not a series. No per-month editing, no history of changes. A series invites a calendar, a "copy last month", and a question about which month's limit a historical comparison should use - none of which was asked for. If per-month planning is ever wanted, that is a new concept with its own screen, not a change to this field.
    Empty means no limit. Zero means nothing should be spent here. They are different, and both are valid. If you do not want the distinction, reject zero - do not silently convert it.
    The pace marker exists because the limit is flat and the month is partial. "3.400 of 6.000" on day 20 is unreadable without it. Position is day / daysInMonth; it is a reference line, never a threshold, and never coloured red.
    Over the limit fills amber and caps the bar at 100%. A capped bar cannot express how far past it went, so the overage is always stated in words beside it. On a phone there is no adjacent column, so that sentence goes underneath - never omitted.
    A list row splits the amber into two segments. The part up to the limit is --amber-2; the overage beyond it is --amber-3, one step paler, so the row shows both how much the limit was and how far past it went inside the same 100% track. The edit page has room for the sentence instead, and uses the single fill.
    Four fills in total, and no others. --green under the limit, --amber-2 up to a limit that has been passed, --amber-3 for the overage segment, and the bare --surface-2 track when no limit is set. Red never appears on a limit bar - it would read as a blocked save.

    5j Merge, and moving orders
    Merging one record into another, for both kinds. The source's orders move to the target and the source is deleted. Irreversible, and confirmed by naming the number of orders that will move.
    Notes for implementation
    Merging a vendor: the source's orders move to the target, its name and aliases become the target's aliases, and the source is deleted. Moving the aliases is the important half - without it the next receipt recreates the duplicate.
    The comparison shows which value wins per field. The target keeps its own unless the source has one and the target does not. Nothing is silently blended, and the user can see the result before agreeing to it.
    A category merges the same way, with less to combine. Its orders move to the target and it is deleted; there are no aliases to carry, and the target keeps its own limit. Same dialog, same confirmation shape.
    The target list is every category except the source. Merging a record into itself is the one selection that cannot be allowed, so it is absent from the list rather than shown and refused. Since categories are multi-valued, an order already carrying both ends up with one label, not a duplicate.
    Merging is not required in order to delete. It is for when the orders belong in another category. A category can be deleted outright from 5f, which takes the label off its orders and leaves their other categories alone - and an order with none at all is allowed, since the field is optional.
    Not reversible, and the dialog says so. Undo is the pattern everywhere else, but this moves rows across records; write an audit record instead of promising a rollback you cannot do.
    Suggested merges are advisory. Normalised name similarity above 0.85, or an identical VAT number. Never merged automatically, at any confidence - the cost of a wrong merge is unrecoverable.
    The count is the last thing in the button. "Merge 2 orders", not "Confirm" - a number the user reads on the button is one they cannot claim not to have seen.

    5k Both tables at every width
    Same rule as 2i: columns are dropped whole, never squeezed until their content wraps. What differs is which column can go, because the two tables answer different questions - a vendor list is about how much and how recently, a category list is about a limit and how close this month is to it. Both tables are the ones 5a and 5d draw, at the widths the list column takes.
    Notes for implementation
    Vendors drop last order, and nothing else. Orders and saved are not columns at any width - they are the name's second line, where a vendor with 38 orders and one with 2 read as different kinds of vendor without costing a track. That leaves two columns to defend, and the date is the one that can go: it joins the second line at 880 in its short form, so the row still says when you last bought there. Spend never leaves - it is what the list is sorted by.
    Categories drop the monthly limit. It is the only column that can go, because the gauge in this month is already drawn against it - the limit's own figure is a second statement of something the row shows. It joins the name's second line at 880 rather than vanishing, since a category without its limit is just a name. The order count and the 12-month average are not columns at any width; they are the second line, the same as a vendor's. This month never leaves.
    The progress bar is a column, not decoration. It stays at every width and goes full width on the phone, where it becomes the row's primary shape. Over the limit it fills amber and the overage is stated in words underneath - a bar pinned at 100% cannot say how far past it went, and on a phone there is no adjacent column to say it for you.
    The edit page is why these tables can shed columns at all. A row is one click from the full record (5c), so anything a narrow table drops is still exact one screen away. The tables become cards at a list column of 640px or less, the order list's rule (2i); above that the 880 table holds, with the last order or the limit on the second line. Below 900px the edit page's rail moves above its form, as the order page's does (Responsive reference 18a).
    Same three implementation rules as 2i. Container queries on the list column, not the viewport - this list is the full width of the page, and on the edit page the same table sits beside a 360px rail, so its width is never the window's. One grid definition shared by header and rows, declared once and overridden per breakpoint. And min-width: 0 on every fluid cell, with the ellipsis triple on every text cell: without it a grid child refuses to shrink below its content and the row overflows instead of truncating.
    The identity mark never shrinks and never drops. The row mark, 42px, at every width. It is the fastest way to find a row, and it is the only thing in the row that survives on a phone unchanged.

    5l Default categories - set here, offered there
    A vendor can carry categories it usually gets filed under. They do nothing on the vendor page - they exist to be offered on an order the moment that vendor is chosen. Four states, in the order a user meets them.
    Notes for implementation
    Add both adds the suggested categories to the order's category field. Nothing else changes.
    Offered, never applied. Choosing a vendor fills the categories field with the vendor's defaults and says where they came from. The user can remove any of them before saving, and the order stores what is in the field at save - not a reference to the vendor's list.
    It fills only when the field is empty. If the user already picked categories, or a scan read one, choosing a vendor leaves them alone and offers its defaults as an add - a suggestion the user acts on, not a replacement.
    Changing the vendor clears what the previous vendor suggested, and nothing else. Track which chips arrived as suggestions; a chip the user added by hand survives every vendor change. Without that flag the only correct behaviour is to leave everything, which strands the wrong categories on the order.
    The suggestion notice is not an error, a warning, or a toast. It is one muted line under the field, and it disappears the moment the user edits the field. It never uses amber or red - nothing is wrong, and nothing is blocked.
    Editing a saved order does not re-suggest. Defaults apply to the first vendor choice on a new order. Reopening an order months later and touching the vendor field must not quietly rewrite categories the user settled at the time.
    Deleting a category takes it off its orders, past ones included, and off the vendor's default list (5f).
    Leave out of statistics is a vendor default too, set in Defaults for its orders (5b, 5c), off by default. Choosing the vendor on a new order sets the order's switch to the vendor's value, by hand and from a scan alike. A switch the user has touched on the order is theirs: changing the vendor afterwards leaves it. A switch not touched follows the vendor, so changing to a vendor with it off turns it back off. The order shows no line saying the vendor set it; the switch shows its state and nothing more. An order imported (11b) or scanned and matched to the vendor takes the default the same way. A copy (8a) keeps the source's value instead.
    Changing the vendor's default changes no saved order, and nothing asks. Turning it on for a vendor with orders applies to new orders only; Save saves the vendor and that is all. Like default categories, the order stores its own value at save. Editing a saved order and changing its vendor does not reset the switch either.
    Default categories and Leave out of statistics are the only vendor defaults. Status is not one.
    Nothing is learnt automatically. Filing three orders under Decor does not make Decor a default. The list is only ever what the user typed on the vendor page - a guess that edits itself is one nobody can predict.

    5m Company details from the CVR register
    A Danish vendor's CVR number links it to the CVR register, and a background job keeps its address current. Six states of the vendor's Country, CVR and Address fields, in 5b and 5c.
    Notes for implementation
    Nothing is looked up while the page is open. A background job does every lookup. A newly saved CVR number is looked up within a day (state 1); after that every vendor with a CVR is checked once a week.
    The register always wins. With a CVR number, Address is not a field: it shows what the register holds, with "From the CVR register, checked 14 Oct." (state 2). A change in the register replaces it silently at the next check. The register's company name (Indbo Møbler A/S) is stored beside the vendor's own Name and printed as the invoice's From; the vendor's Name never changes.
    Addresses are kept with the date they took effect. An invoice uses the address the vendor had on the order date (Invoice 24a), so an old order's invoice does not change when the company moves.
    A Danish vendor without a CVR number is searched by name in the same job (cvrapi.dk's name search). The single best match is offered on the vendor page as "Is this the company?" (state 3). Use it sets the CVR number and the address follows at once, from the result. Not this one closes it, and that name is not searched again until the vendor's Name changes. A vendor with no match shows nothing.
    A company that has ceased trading keeps its last address, and the help line reads "Ceased trading 3 Mar 2026." (state 4). Nothing else changes: the vendor is not archived and its orders are untouched.
    A CVR number the register does not know is marked on the field at the next visit, "No company has CVR 12345679 in the register. Check the number." (state 5). Address goes back to a typed field. The job tries again only when the number is changed.
    Lookups use cvrapi.dk's free tier: 50 a day, called from the server with a user agent naming Spendly and a contact, as cvrapi.dk asks. The weekly check spreads its lookups over the week, at most 40 a day, so 10 stay free each day for the invoice dialog's live lookup (Invoice 24c) and for newly saved CVR numbers, which go first. When the limit answers, the job stops for the day and what is left waits for the next day. Nothing is shown to the user: a vendor waiting keeps state 1 or its last checked date. A result is used for every vendor with the same CVR number, so it is looked up once.
    Only Danish companies are in the CVR register. Country defaults to Denmark. Any other country (state 6) replaces CVR with a typed VAT number and keeps Address typed; the job never looks it up, by number or by name. Country is printed on an invoice only when it is not Denmark.
