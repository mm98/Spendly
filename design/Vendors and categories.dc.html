5a Vendors
A vendor is mostly read-only: it earns its numbers from orders. So the list leads with spend and order count, and the panel on the right is the selected vendor — contact details you can edit, its recent orders, and merge for the duplicates that scanning creates.
NOTES FOR IMPLEMENTATION
The row menu is drawn open above. Delete is disabled while the vendor has orders, with the count beside it saying why — merge or archive are the ways out. Enabling it and failing on click teaches nothing; the count is the explanation.
Archive, not delete, is the normal end of a vendor's life. Archived vendors leave the list and the facets but keep their orders, which is why the Active/Archived toggle exists in the toolbar.

5b Categories
Categories carry the monthly limit, so the list is the budget overview: limit, this month against it, and the twelve-month average that tells you whether the limit is realistic. The panel is the category form — name, icon, colour and the limit, which is what Statistics reads. Icon and colour travel together: the icon is picked from a fixed set and rendered in the category colour, so chips, facets and charts stay recognisable.
NOTES FOR IMPLEMENTATION
The row menu is drawn open above. Change monthly limit is a shortcut into the panel field, not a separate dialog — it selects the row and focuses the limit input, because a dialog for one number that already has a home is a second place to maintain.
Delete is disabled while the category is in use. A category cannot be archived — unlike a vendor, it is a label the user invented, so the way out is reassigning its orders.

5d Vendor aliases
A receipt rarely prints the name you call a vendor. "INDBO MØBLER A/S", "Indbo Møbler ApS" and a webshop's "indbo.dk" are one vendor, and the aliases are what let a scan land on it without asking. They are also where a merged vendor's old names go, so nothing stops matching after a merge.

"Also matches", not "Aliases". The label states what the field does. A user adding a name here is teaching the scanner, and the wording should make that obvious without a hint.
Chips with onRemove, from 14a — one component, and removing is the only edit. To correct a typo, remove and re-add; an editable chip needs an inline text state nothing else in the app has.
A CVR number is an alias like any other. It matches exactly rather than fuzzily, and it is the strongest signal a scan can find — a receipt with a matching CVR resolves without a confidence flag.
Merged names are kept and marked. After merging "Indbo Interiør" into this vendor, its name becomes an alias here — otherwise the next receipt from the old name creates the duplicate again.
An alias is never displayed as the vendor. Orders, lists, charts and the identity mark all use the canonical name — the alias only exists to be matched against.
HOW A SCAN LEARNS ONE
Vendor
IM Indbo Møbler
Also match INDBO MØBLER A/S in future
The name printed on this receipt
Shown in scan review (3a) only when the receipt's name differs from the vendor chosen, and only once per name. Checked by default.
Learning is opt-out, not automatic. The checkbox is on by default because the common case is correct, but a user who picked the wrong vendor should not silently teach the scanner a wrong name.
It appears once per distinct receipt name. If the alias already exists, nothing is shown — a checkbox offering to learn something already known reads as a bug.
The alias is written when the order is created, not when the box is ticked. A discarded scan teaches nothing, in keeping with "a scan proposes, it never writes".
The same pattern is not offered for categories. A category is the user's own classification, not a name printed on paper.
MATCHING ORDER
1
Exact CVR. Resolves outright, no confidence flag.
2
Exact alias or name, normalised — case, punctuation, and the company suffixes A/S, ApS, IVS, Ltd removed. Resolves outright.
3
Fuzzy above 0.9 against names and aliases alike. Pre-selected, but marked uncertain.
4
Nothing. The picker opens with near matches and a "Create" row, as in 3a.
An alias is never shared. If a name would match two vendors it belongs to neither — reject it on entry, naming the vendor that already claims it.
EVERYWHERE ELSE
Search matches aliases — the order list field, the vendor combobox and the palette (9d). A match on an alias shows the canonical name with the matched alias beside it in muted 12px: "Indbo Møbler — matched indbo.dk". Without that line the result looks like it does not contain the query.
Facet counts are not affected. One vendor is one facet value whatever it is called.
Identity marks derive from the canonical name only (14f), so the mark does not change when a receipt uses a different name.
Duplicate detection reads aliases too (5c). Two vendors sharing a normalised alias are a stronger duplicate signal than similar names.
Import matches on them as well, which is what lets a spreadsheet column of messy vendor names resolve without a mapping row each.

The target always wins a contested field. No per-field radio buttons: a merge with five choices in it is a form, and the user picked a direction already by choosing what to merge *into*. The comparison exists to show what that direction costs, not to negotiate it.

NOTES FOR IMPLEMENTATION
Vendors drop saved first, then orders. Saved is the softest number here — it is a nice-to-know, and the panel states it exactly for whichever vendor is selected. Orders survives one step longer than saved but folds into the name's second line at 880 rather than vanishing, because a vendor with 24 orders and one with 2 are different kinds of vendor. Spend and last order never leave: spend is what the list is sorted by, and nothing else on the screen says when you last bought from someone.
Categories drop the 12-month average first. It is context for the limit, not the limit itself. The limit and this month never leave — they are the pair the whole page exists to compare, and a category row without both is just a name.
The progress bar is a column, not decoration. It stays at every width and goes full width on the phone, where it becomes the row's primary shape. Over the limit it fills amber and the overage is stated in words underneath — a bar pinned at 100% cannot say how far past it went, and on a phone there is no adjacent column to say it for you.
The panel is why these tables can shed columns at all. Both screens are list-plus-panel (5a), so anything dropped is one click away and still exact. Below 900px the panel becomes a separate view, which is also where the tables become cards — the two changes are the same change.
Same three implementation rules as 2i. Container queries on the list column, not the viewport — this list sits beside a 400px panel, so its width is never the window's. One grid definition shared by header and rows, declared once and overridden per breakpoint. And min-width: 0 on every fluid cell, with the ellipsis triple on every text cell: without it a grid child refuses to shrink below its content and the row overflows instead of truncating.
The identity mark never shrinks and never drops. 34px at every width. It is the fastest way to find a row, and it is the only thing in the row that survives on a phone unchanged.

NOTES FOR IMPLEMENTATION
The summary mirrors the form, live. It redraws as fields change, so the preview row is the row the list will draw. It is not a saved state — nothing in it survives Cancel.
Initials are derived, never typed. First two characters of the name, uppercased; NY before a name exists. There is no initials field.
The figure at the foot is money, not a limit. Both cards end on spend all time, even though the category form owns a limit field — restating one of the form's own inputs as its bottom line says nothing the field above did not.
VIEW ORDERS only when the record exists. A record being created has no orders to list, so the button is absent rather than disabled. It opens the order list filtered to this record.
The delete card is edit-only, and it states the constraint before the button rather than after the click. The refusal itself is the server's — a 409 naming how many orders are in the way, surfaced as a negative toast.
Favourite is a checkbox row, not a switch. It lands on save with the rest of the form, and a switch that needs a save is a checkbox wearing the wrong costume. Settings' immediate toggles are the ones that stay switches — see 14a.
