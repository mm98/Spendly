SPENDLY · DESIGN MOCKUPS

Order tracking for personal receipts, from capture to what it all added up to.

Eighteen files, forty-six screens. It started with one problem — the order header took too much room above the items — and grew into the flows around it: the list, creating from a scanned receipt, statistics, vendors and categories, the states in between, and the phone.

Every screen carries a visible id badge, unique across the whole set, so it can be pointed at in review.

Recreate them in the existing codebase using its patterns — do not copy the files in. support.js is a preview harness with no place in the product. • Container queries, not media queries. WHERE THE CODE GOES

Paste this alongside the prompt. Without it, files land wherever the current task happened to be, and the same component gets built twice under two names.

Folder structure src/ components/ the control set from 14d — nothing app-specific Field/ the shared wrapper, and it owns label + error Field.tsx Field.module.css index.ts TextField/ AmountField/ Combobox/ the big one — may hold useCombobox.ts, Option.tsx Button/ Chip/ …one folder per component, same three files layouts/ the four container-query wrappers from 18a MainWithRail.tsx RailWithMain.tsx ListWithPanel.tsx CardGrid.tsx features/ app-specific, grouped by thing not by type orders/ OrderList.tsx screen OrderDetail.tsx screen OrderEdit.tsx screen ItemLineRow.tsx used only by orders ItemLineEditor.tsx useOrderDraft.ts orders.api.ts orders.types.ts scan/ statistics/ vendors/ categories/ settings/ shell/ Sidebar, TopBar, CommandPalette, ToastHost, DialogHost lib/ formatMoney.ts, parseAmount.ts, dates.ts styles/ tokens.css, themes.css, reset.css The one rule that decides placement Used by two or more features → components/. Used by one → that feature's folder. Don't pre-promote something to components/ because it looks reusable; move it when the second caller appears. Naming • Components and screens: PascalCase.tsx, one component per file, file named after the export. No index.tsx holding a component — index.ts is a re-export only, so stack traces and tabs stay readable. • Hooks: useThing.ts. Utilities: camelCase.ts. Types: thing.types.ts. API access: thing.api.ts. Styles: Component.module.css beside it. • Name by what it is, not what it looks like or where it sits: ItemLineRow, not GreenRow or LeftColumnItem. A name containing a colour, a position, or a screen name will be wrong after one change. • No utils.ts, helpers.ts, common/, shared/, misc/. Every one of those becomes a bin nobody can safely delete from. Name the file after the thing it does: parseAmount.ts. • No New, V2, Old, Wrapper, Container, Base, Enhanced in a name. If two versions must coexist, the reason goes in a comment, not the filename. • Booleans read as questions: isDirty, hasAttachments, canEdit. Handlers are onX as props, handleX as implementations. • One concept, one word, everywhere — in code, tests, API and copy. It is vendor (never supplier or merchant), category (never tag or group), item line (never product, article or row), attachment for a file on an order, photo for the image on an item line, limit for the monthly category amount (never budget). Renaming these later touches everything. Screens map to routes, one file each / Home · /orders OrderList · /orders/:id OrderDetail · /orders/:id/edit OrderEdit · /orders/new NewOrder · /scan Scan · /statistics Statistics · /vendors Vendors · /categories Categories · /settings/:section Settings · /import Import Edit is a route, not a toggle — it has to be linkable and survive Back. Don't create A pages/ folder next to features/ (screens live with their feature) · a folder for one file · a barrel file re-exporting everything in components/ (it defeats tree-shaking and hides real dependencies) · a designSystem/ or ui/ folder duplicating components/ · tokens.js — tokens are CSS custom properties in styles/, read by both themes. Vite specifics index.html stays at the project root, not in public/ — it is the entry Vite transforms, and it loads /src/main.tsx as a module. src/main.tsx mounts the app and imports the global stylesheets from styles/ in order: reset, tokens, themes. Nothing else imports them. public/ is only for files served verbatim at a stable URL (favicon, robots.txt). Fonts and images that components reference go in src/ and are imported, so they get hashed filenames and long-cache headers. Set one alias in vite.config.ts — @ → ./src — and mirror it in tsconfig.json paths. Relative imports beyond ../ make a file impossible to move, which is the whole point of the structure above. Route-level code splitting with React.lazy per screen: statistics and import pull in the most and are visited the least. Theme is applied before first paint by a small inline script in index.html that reads the stored preference and sets a data attribute on <html>. Doing it in React costs a flash of the wrong theme.

Written for Vite + React with TypeScript and CSS Modules. If the project uses .jsx, plain CSS or a styling library, keep its conventions — the folder boundaries and naming rules are what matter, not the file suffixes.

WHY IT IS SHAPED THIS WAY

Six principles produced every rule above. They are here so the rules can be extended rather than just followed — a new case that isn't listed should be settled by working out which principle applies.

1
Group by what changes together, not by what things are
A change to how order editing works touches its screen, its row component, its draft hook and its API call. In a type-grouped tree those sit in four distant folders and the change is four unrelated diffs; in a feature folder it is one. components/ is the exception because a control genuinely does change independently of any feature.
2
Let the second caller do the promoting
Something built in a feature folder and moved to components/ when a second feature needs it arrives with a known set of requirements. Something placed in components/ up front is designed against a guess, and its props end up shaped for a use that never came. Moving a file is cheap; unpicking a speculative API is not.
3
A name should survive the next change
Names describing appearance or position — GreenRow, LeftColumnItem, WideCard — are wrong the moment the design moves, and then either mislead or force a rename that touches every import. Naming by what a thing is means the name outlives its styling. The same reasoning rejects V2 and New: they describe a moment in the project's history, and that moment passes.
4
One concept, one word, in every layer
When the database says supplier, the code says vendor and the UI says merchant, every conversation and every search needs a translation step, and a bug report can't be traced to a line of code. The vocabulary list is short and deliberately dull. It is also why limit is never called budget: the design decided a limit does not block a save, and calling it a budget invites someone to make it behave like one.
5
No folder or file may be a bin
utils, helpers, shared, common, misc all share one property: nothing can be ruled out of them, so they only ever grow, and nobody can delete from them safely because there is no way to know what a given function was for. A file named after the thing it does — parseAmount.ts — states its own scope, and an unused one is obviously unused.
6
Optimise for reading, not for typing
One component per file named after its export means a stack trace, a tab bar and a search result all name the thing you want. Twelve files called index.tsx save a few characters at the import site and cost that clarity everywhere else. The same trade rejects the barrel file over components/: one convenient import line, in exchange for hidden dependencies and a tree that can't be shaken.

The through-line is that all six trade a small, immediate convenience for the ability to change things later. That is the right trade here specifically because this is a design handoff — every screen in this index is going to move at least once after it ships.

RULES EVERY SCREEN FOLLOWS
The top shell is locked
No page actions live up there. Everything a page does belongs to the page.
A limit never blocks a save
Red blocks, amber informs. A monthly limit is a fact about your month, not a rule.
Nothing saves by itself
Scans propose, they never overwrite. A duplicate opens unsaved and can still be abandoned.
Numbers answer the current filter
Totals and counts reflect what is on screen, not the whole account.
Single user, personal receipts
No item catalogue, no shared editing, no permissions. A conflict means two tabs, not two people.

These are design references, not production code: layout and states only, no data or behaviour. Where a mockup and the code disagree, the code is the current truth — the mockup is the proposal.
